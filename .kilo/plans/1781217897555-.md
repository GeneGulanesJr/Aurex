# Plan: Persistent Data + In-App Update System

## Problem

When running `docker compose build && docker compose up`, all user data (GitHub login, PiNyx API keys, session state, mission history) is lost because **LaPis** — the service that stores all persistent state — has **no named Docker volume**. Its data lives only inside the container filesystem.

Additionally, the user wants:
1. An **in-app update notification** when code changes are detected
2. An **"Update" button** in the frontend to trigger a rebuild without losing data

---

## Part 1: Fix Data Persistence

### Root Cause
- **LaPis** (`Dockerfile.lapis`) stores all state (KV settings, missions, milestones, etc.) at `/root/.pi/memory` inside the container. No named volume is defined for it.
- **PiNyx** already has `pinyx-data:/data` ✅
- **Backend** is stateless (delegates to LaPis) ✅
- **Frontend** is stateless (nginx static files) ✅

### Changes

#### 1.1 `docker-compose.yml` — Add LaPis named volume
```yaml
services:
  lapis:
    volumes:
      - lapis-data:/root/.pi    # persist LaPis memory/state
      - ${REPO_ROOT:-/tmp}:/workspace

volumes:
  pinyx-data:
  lapis-data:       # NEW
```

This is the **only docker-compose.yml change needed**. One volume addition solves the entire data loss problem.

#### 1.2 Update the usage comment at the top of docker-compose.yml
```
# Usage:  docker compose up --build -d    (rebuild + restart, data persists)
# Stops:  docker compose down             (data persists in volumes)
# Reset:  docker compose down -v          (destroys volumes too)
```

## Part 2: In-App Update Detection & Notification

### Architecture Overview

```
Remote repo (main branch)
  ↓ git fetch origin main (daily at 8am + on-demand)
Backend compares local HEAD vs origin/main
  ↓ (new commits found)
WebSocket event: "update_available"
  ↓
Frontend shows pulsing notification + "UPDATE" button in TopBar
  ↓ (user clicks Update)
Backend writes flag file: /aurex/.update-pending
  ↓
Host cron job (every 1 min) detects flag file
  ↓
Cron runs: git pull → docker compose up --build -d → rm flag
  ↓
Containers rebuild & restart, data persists in volumes
  ↓
Frontend WebSocket auto-reconnects, notification clears
```

**No Docker socket mounted.** The backend only writes a flag file. A cron job on the VPS host does the actual rebuild. This keeps the backend container isolated from Docker.

### Changes

#### 2.1 `docker-compose.yml` — Make `/aurex` writable (no Docker socket)
```yaml
services:
  backend:
    volumes:
      - ${REPO_ROOT:-/tmp}:/workspace
      - .:/aurex       # CHANGED: read-write (backend needs to write .update-pending flag)
    environment:
      ...
```

Note: `/aurex` mount changed from `:ro` to read-write so the backend can write the `.update-pending` flag file. **No Docker socket is mounted.**

#### 2.2 Host-side: Update cron script `scripts/cron-update.sh` (NEW)

A shell script deployed to the VPS that the cron job runs:

```bash
#!/bin/bash
# /path/to/aurex/scripts/cron-update.sh
# Add to crontab: * * * * * /path/to/aurex/scripts/cron-update.sh >> /var/log/aurex-update.log 2>&1
PROJECT_DIR="$(cd "$(dirname "$0")/.." && pwd)"
FLAG="$PROJECT_DIR/.update-pending"

if [ -f "$FLAG" ]; then
  echo "[$(date)] Update flag detected. Starting rebuild..."
  rm -f "$FLAG"
  cd "$PROJECT_DIR"
  git pull origin main
  docker compose up --build -d
  echo "[$(date)] Rebuild complete."
fi
```

User adds this to their VPS crontab (instructions provided in deploy docs).

#### 2.3 Backend: New route file `packages/backend/src/routes/update.ts`

**Endpoints:**

| Method | Path | Purpose |
|---|---|---|
| `GET /api/update/status` | Returns `{ updateAvailable: boolean, currentSha: string, latestSha: string, behindBy: number, lastChecked: string }` |
| `POST /api/update/check` | Manually triggers `git fetch origin main` and re-checks for new commits |
| `POST /api/update/apply` | Writes `.update-pending` flag file (safe — no Docker access needed) |

**Update detection logic:**
- On startup, capture current HEAD SHA via `git rev-parse HEAD` in `/aurex`
- **Scheduled check:** Every day at 8am (user local time), run `git fetch origin main` then compare `git rev-parse HEAD` vs `git rev-parse origin/main`. If `origin/main` is ahead → emit WebSocket `update_available` event.
- **Manual check:** `POST /api/update/check` triggers immediate `git fetch` + comparison
- Store `lastChecked` timestamp so the frontend can show when the last check occurred

**Update apply logic:**
1. Write empty file `.update-pending` in `/aurex/` directory
2. Return `{ started: true }` immediately
3. Host-side cron job picks up the flag within ~1 minute and does the actual rebuild
4. Backend container gets replaced → naturally shuts down
5. All data persists in volumes (Part 1)

**WebSocket integration:**
- Add `update_available` event type to the existing EventBus
- Push to all connected clients when new commits are detected

**Daily 8am check implementation:**
- Use `setTimeout`-based scheduling (no external cron library needed)
- Calculate ms until next 8am local time, set timeout, recurse
- On check: fetch → compare → emit event if update found

#### 2.6 Frontend: New hook `packages/frontend/src/hooks/useUpdateStatus.ts`

```ts
// Listens for WebSocket "update_available" events
// Also fetches /api/update/status on mount
// Returns { updateAvailable, currentSha, latestSha, behindBy, lastChecked, applyUpdate, applying, checkNow }
```

- On mount: `GET /api/update/status`
- On WebSocket `update_available` event: update state
- `applyUpdate()`: calls `POST /api/update/apply`, sets `applying: true`
  - After calling, start polling `GET /health` every 2s
  - Once health check succeeds → WebSocket auto-reconnects → state clears
- `checkNow()`: calls `POST /api/update/check` for manual refresh

## VPS Deployment

After deploying, the user sets up the cron job once:

```bash
chmod +x scripts/cron-update.sh
# Add to crontab:
crontab -e
# Add this line:
* * * * * /path/to/aurex/scripts/cron-update.sh >> /var/log/aurex-update.log 2>&1
```

After that, updates are fully automatic from the UI:
1. Backend checks for new commits daily at 8am (and on demand)
2. Frontend shows a notification when updates are available
3. User clicks "Update" → flag file written → cron rebuilds within ~1 minute
4. All data persists in Docker volumes — no re-login needed
