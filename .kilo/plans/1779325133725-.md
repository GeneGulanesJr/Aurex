# Fix SQLITE_BUSY "database is locked" during concurrent access

## Root Cause

When one Pi instance is running `index-repo` (which holds the WAL write lock inside long transactions), another instance calling `session-start` fails after `busy_timeout=5000ms` (5 seconds) with `SQLITE_BUSY`. Indexing operations can take 30+ seconds per batch.

**Why WAL mode alone doesn't solve this:** WAL allows concurrent **readers** but still only one **writer** at a time. Both `index-repo` and `session-start` need to write, so they compete for the single write lock.

**Contributing factors:**

- `busy_timeout=5000ms` is far too short for indexing workloads
- No application-level retry logic on `SQLITE_BUSY` errors
- Doc indexing uses auto-commit (no transaction wrapping), causing thousands of individual lock acquisitions

## Plan

### 1. Increase default `busy_timeout_ms` from 5000 → 30000 (30s)

**File:** `config.js` (DEFAULTS object)
**Rationale:** Indexing batch transactions can take 10-30s. A 30s timeout gives short operations (session-start, memory-save) enough headroom to wait out an indexing transaction. Users can still override via config.

### 2. Add application-level retry wrapper in `db.js`

**File:** `db.js` — add retry logic to `_sqlJson()` and `_sqlRun()` / `_sqlAll()`
**Approach:**

- Catch `SQLITE_BUSY` (rawCode 5) errors
- Retry with exponential backoff: 100ms, 200ms, 400ms... up to a configurable max retries (default 5)
- Total possible wait: ~1.5s from retries + 30s from SQLite's own busy_timeout = ~31.5s
- Log a warning on retry (not on first attempt)
- This handles the edge case where busy_timeout expires but the operation is still recoverable

### 3. Wrap `sessionStart` SQL operations in a transaction

**File:** `src/memory-domain/sessions.js`
**Approach:** Use `deps.withTransaction()` to wrap the 4 SQL statements in `sessionStart()` into a single transaction. This reduces lock acquisitions from 4 to 1 and makes the operation atomic.

### 4. Wrap doc indexing in a transaction

**File:** `src/doc-index/repos.js`
**Approach:** Wrap the batch INSERT operations in `indexDocs()` inside a single transaction (or batched transactions similar to code indexing). This reduces thousands of individual write-lock acquisitions to a few batch transactions.

### 5. Update config default documentation

**File:** `config.js` — update comment for `busy_timeout_ms` to explain the new default and when to tune it.

## Files to Modify

| File                            | Change                                               |
| ------------------------------- | ---------------------------------------------------- |
| `config.js`                     | Change `busy_timeout_ms` default from 5000 to 30000  |
| `db.js`                         | Add SQLITE_BUSY retry logic with exponential backoff |

## Risk Assessment

- **Low risk:** Increasing busy_timeout only affects how long SQLite waits before giving up — longer waits are always safer.
- **Low risk:** Retry logic only activates on SQLITE_BUSY, all other errors pass through unchanged.
- **Medium risk:** Wrapping sessionStart in a transaction changes lock scope — but since the operations are all related, atomicity is actually better.
- **Low risk:** Wrapping doc indexing in transactions reduces total lock time and contention.
