# Plan: Index Performance Optimizations — Phase 2 (Corrected)

## Summary

Building on the existing worker thread pool implementation, this plan addresses the actual remaining bottlenecks in the indexing pipeline. The original plan had several issues: proposed async changes to synchronous code, ignored SQLite's single-writer constraint, recommended redundant optimizations, and missed the most impactful opportunities.

Target: 3-5x overall speedup for large repositories (500+ files).

## Current State Analysis

### Already Implemented
- [x] Worker thread pool for parallel AST parsing (`WORKER_POOL.MIN_FILES_FOR_PARALLEL: 50`, `WORKER_POOL.MAX_WORKERS: 4`)
- [x] Batch processing with `RESULT_LIMITS.INDEX_BATCH_SIZE: 50`
- [x] AoS→SoA symbol data split for cache efficiency
- [x] Prepared statement reuse for bulk symbol inserts (`insertSymbolBulk`)
- [x] WAL mode, NORMAL synchronous, MEMORY temp store for SQLite
- [x] Incremental reindexing via git diff or content hash comparison
- [x] Adaptive progress throttling via `shouldEmitFileProgress()`
- [x] Single-pass symbol index construction (7 Maps built in one loop)

### Actual Remaining Bottlenecks (in priority order)

1. **Double parsing**: Every file is parsed TWICE — once in `extractSymbolsSplit()` for symbols, then again in `writeRecords()` via `registry.parseTree()` for scope bindings. The tree is discarded after symbol extraction and re-parsed for scope bindings. (~15-20% of parse time wasted)

2. **Import graph `resolveImportTarget()` SQL storm**: For each import, calls `db.prepare('SELECT id FROM code_files WHERE repo_id = ? AND path = ?')` up to 11 times with non-reusable prepared statements. For a repo with 500 files × 10 imports × 6 avg candidates = 30,000 redundant SQL queries. (~30-40% of import graph time)

3. **Incremental reindex uses per-symbol inserts**: `reindexRepository()` calls `insertSymbolsSplit()` which does `repository.insertSymbol()` one at a time, unlike the full index path that uses `insertSymbolBulk()`. Also no worker pool usage.

4. **Derived phases are sequential**: Import graph, scope resolution, call graph, and complexity are built sequentially. No overlap.

## Implementation Plan

### Phase 1: Eliminate Double Parsing (High Impact, Low Risk)

**File:** `src/code-index/symbol-extractor.js`, `src/code-index/incremental-indexer.js`

**Problem:** `extractSymbolsSplit()` calls `registry.parseContent()` internally (line 143 of symbol-extractor.js), which parses a tree-sitter tree, extracts symbols, and discards the tree. Then `writeRecords()` calls `registry.parseTree()` (line 753 of incremental-indexer.js) which parses the SAME content again to get the tree for scope binding extraction.

**Solution:** Return the parsed tree from `extractSymbolsSplit()` so `writeRecords()` can reuse it.

#### Step 1.1: Modify `_parseRawSymbols()` to optionally retain the tree

```javascript
// symbol-extractor.js — _parseRawSymbols()
// Change: After reg.parseContent(), also call reg.parseTree() once and return the tree
// OR: modify parseContent() in parse-code.js to also return the tree object
```

The key decision is whether to:
- **Option A**: Call `reg.parseTree()` inside `_parseRawSymbols()` and return `{ rawSymbols, source, callees, tree }` — requires `parseTree()` to exist and work on the same content
- **Option B**: Modify `parseContent()` in `parse-code.js` to return both symbols AND the tree — requires changing the parser interface

**Recommended: Option A** — it doesn't change the parser interface, just the extractor's output.

```javascript
// symbol-extractor.js
function _parseRawSymbols(filePath, reg, content) {
  if (!reg.canParseFile(filePath)) {
    return { rawSymbols: [], source: '', callees: [], tree: null };
  }
  let rawSymbols;
  let source = content;
  if (content !== undefined) {
    rawSymbols = reg.parseContent(filePath, content);
  } else {
    rawSymbols = reg.parseFile(filePath);
    try { source = require('fs').readFileSync(filePath, 'utf-8'); } catch { source = ''; }
  }
  let callees = [];
  if (source && typeof reg.extractCalleesFromContent === 'function') {
    try { callees = reg.extractCalleesFromContent(filePath, source); } catch {}
  }
  let tree = null;
  try {
    const result = reg.parseTree(filePath, source || content);
    tree = result ? result.tree : null;
  } catch {}
  return { rawSymbols, source, callees, tree };
}
```

#### Step 1.2: Thread the tree through `extractSymbolsSplit()`

```javascript
// symbol-extractor.js

    hot.push(h);

```


**Expected impact:** ~15-20% reduction in total parse time (eliminates redundant tree-sitter parse for every file)

### Phase 2: Import Graph — Pre-build File Path Map (High Impact, Low Risk)

**File:** `src/code-analysis/import-graph-impl.js`

**Problem:** `resolveImportTarget()` (line 179-208) calls `db.prepare('SELECT id FROM code_files WHERE repo_id = ? AND path = ?').get(repoId, candidate)` up to 11 times per import. The `db.prepare()` call creates a new prepared statement object each time (it's not reusing a cached prepared statement). For a 500-file repo with ~5000 imports, this results in ~30,000+ SQL prepare+query calls.

**Solution:** Pre-load all file paths into a `Map<path, fileId>` at the start of `buildImportGraph()`, then resolve imports with pure in-memory lookups.

#### Step 2.1: Build a path→fileId Map before the loop

```javascript
// import-graph-impl.js — buildImportGraph()

  const files = db.prepare('SELECT id, path FROM code_files WHERE repo_id = ?').all(repoId);
  const contentStmt = db.prepare('SELECT content FROM code_files WHERE id = ?');

  // NEW: Pre-build path resolution map
  const filePathMap = new Map();
  for (const file of files) {
    filePathMap.set(file.path, file.id);
  }

  // ... rest of the function ...
}
```

#### Step 2.2: Replace `resolveImportTarget()` to use the Map

```javascript
// Replace the current function that does SQL queries:
function resolveImportTargetLocal(filePathMap, sourceFilePath, targetModule) {
  if (!targetModule.startsWith('.') && !targetModule.startsWith('/')) {
    return null;
  }
  const sourceDir = path.dirname(sourceFilePath);
  const resolved = path.resolve(sourceDir, targetModule);

  const candidates = [
    resolved,
    `${resolved}.js`,
    `${resolved}.mjs`,
    `${resolved}.cjs`,
    `${resolved}.ts`,
    `${resolved}.mts`,
    `${resolved}.cts`,
    `${resolved}.tsx`,
    path.join(resolved, 'index.js'),
    path.join(resolved, 'index.ts'),
    path.join(resolved, 'index.tsx'),
  ];

  for (const candidate of candidates) {
    const id = filePathMap.get(candidate);
    if (id !== undefined) {
      return id;
    }
  }
  return null;
}
```

Update the loop to call `resolveImportTargetLocal(filePathMap, file.path, imp.target_module)` instead of `resolveImportTarget(db, repoId, file.path, imp.target_module)`.

**Expected impact:** 50-70% faster import graph building (eliminates ~30K SQL queries, replaced with Map lookups)

**Files modified:**
- `src/code-analysis/import-graph-impl.js` — add `filePathMap` + `resolveImportTargetLocal()`

**Est. effort:** 1.5h

### Phase 3: Incremental Reindex — Batch Symbol Inserts (Medium Impact, Low Risk)

**File:** `src/code-index/incremental-indexer.js`

**Problem:** `reindexRepository()` processes files one at a time. For each changed file, it:
1. Calls `insertSymbolsSplit()` which does `repository.insertSymbol()` per symbol (no bulk insert)
2. Wraps each file in its own `repository.withTransaction()` call
3. Does NOT use the worker pool for symbol extraction

**Solution:** Batch the changed files similar to how `parsePhase()` works.

#### Step 3.1: Batch changed files in `reindexRepository()`

Instead of processing each file individually in the `for` loop (lines 996-1096), collect all changed files first, then batch-process them:

```javascript
// Collect changed files

    unchanged++;
  } else {
    changedRecords.push({ filePath, record, prev, fileParams });
  }
}

// Batch insert changed files

for (const { record, prev, fileParams } of changedRecords) {
  let fileId;
  if (prev) {
    repository.clearFileSymbols(prev.id);
    repository.updateFile(prev.id, fileParams);
    fileId = prev.id;

  const { hot: hotSymbols, cold: coldSymbols, tree } = extractSymbolsSplit(filePath, registry, record.content);
  // ... accumulate for bulk insert ...

  }

// Bulk insert all symbols in one transaction

  repository.insertSymbolBulk(allSymbols);

```

When `changedRecords.length >= WORKER_POOL.MIN_FILES_FOR_PARALLEL`, create a worker pool and use `pool.parseAll()` for symbol extraction, same as `parsePhase()`.

**Expected impact:** 2-5x faster reindex for multi-file changes (bulk inserts + worker pool for large changes)

### Phase 4: Derived Phase — Overlap Computation with Writes (Medium Impact, Medium Risk)

**File:** `src/code-analysis/import-graph-impl.js`, `src/code-analysis/call-graph-impl.js`

**Problem:** The original plan proposed `Promise.all(chunks.map(...))` for parallel graph building. This won't work because:
1. Both `buildImportGraph()` and `buildCallGraph()` are **entirely synchronous** functions
2. Both wrap all work in a single SQLite transaction (`runInTx`)
3. SQLite allows only ONE writer at a time — parallel chunks would serialize on the write lock anyway
4. Node.js is single-threaded for CPU-bound work unless using Worker threads

**Solution:** Separate the CPU-bound computation (regex extraction, callee resolution) from the I/O-bound writes (SQL INSERT), and batch the writes.

#### Step 4.1: Import graph — collect edges, then bulk insert

```javascript
// import-graph-impl.js — buildImportGraph()
function buildImportGraph(db, repoId) {
  // ... guard, delete, load files, build filePathMap (Phase 2) ...

  // Phase 1: Extract all import edges (CPU-bound, no writes)
  const edges = [];
  for (const file of files) {
    const contentRow = contentStmt.get(file.id);
    if (contentRow && contentRow.content) {
      const imports = extractImportsFromSource(contentRow.content);
      for (const imp of imports) {
        const targetFileId = resolveImportTargetLocal(filePathMap, file.path, imp.target_module);
        edges.push([repoId, file.id, imp.target_module, targetFileId, imp.import_type, imp.line_number]);
      }
    }
  }

  // Phase 2: Bulk insert all edges in one transaction
  runInTx(() => {
    for (const edge of edges) {
      insertStmt.run(...edge);
    }
  });

  return { success: true, edges: edges.length };
}
```

This is a minor refactor — the computation was already separated from writes within the transaction. The real win is Phase 2 (filePathMap) which eliminates the SQL queries during computation.

#### Step 4.2: Call graph — collect edges, then bulk insert

Same pattern for `call-graph-impl.js`. The current code already does computation and writes interleaved inside the transaction. Separate into:
1. Load all data (symbols, files, content) — already done upfront
2. Process all files to collect call edges in an array — move computation outside transaction
3. Bulk insert in a single transaction — move writes into transaction

This has the benefit of keeping the transaction open for a shorter duration, reducing lock contention.

#### Step 4.3: Overlap import graph and call graph with scope resolution

In `rebuildDerivedIndexes()` (incremental-indexer.js line 312), the four derived phases run sequentially:
1. Build import graph
2. Resolve scope bindings
3. Build call graph
4. Compute complexity

Since import graph and scope resolution are independent (call graph depends on both), we can:
- Run import graph and scope resolution in parallel using `Promise.all()` if we make them async
- Then run call graph (which needs both imports and scope bindings)
- Then complexity (independent, can run in parallel with call graph if scope isn't needed)

However, since all four are currently synchronous and CPU-bound, true parallelism requires Worker threads. For now, just reordering to minimize critical path is sufficient.

**Expected impact:** 10-15% faster derived phase (shorter transaction duration, better sequencing)

**Files modified:**
- `src/code-analysis/import-graph-impl.js` — separate computation from writes
- `src/code-analysis/call-graph-impl.js` — separate computation from writes
- `src/code-index/incremental-indexer.js` — reorder derived phases

**Est. effort:** 3h

## What Was Removed from the Original Plan (and Why)

| Original Step | Why Removed |
|---|---|
| **1.1 Parallel Directory Walking** | Scanner is entirely synchronous (`fs.readdirSync`). Converting to async is a large refactor with minimal benefit — directory walking is I/O-bound on SSDs and the scanner already uses `withFileTypes: true` to avoid extra stat calls. |
| **1.2 Lazy Gitignore Evaluation** | Already implemented. The scanner loads `.gitignore` files only when entering a directory (lines 215-221 of scanner.js), not per-file. The `ignoredBy()` function checks against cached `ignore` instances. |
| **4.1 LRU Cache** | Unnecessary. No `src/cache/` directory exists. No `lru-cache` dependency. The call graph already uses in-memory `Map` indices. The import graph's real issue (per-call `db.prepare()`) is fixed by Phase 2's filePathMap. |
| **4.2 Progress Reporting** | Already implemented. `shouldEmitFileProgress()` (line 78-86 of incremental-indexer.js) already provides adaptive frequency (every 10 for <=100 files, every 25 for >100 files, always for first 5 and last). |

## Testing Strategy

1. **Unit tests** for each optimization
   - Phase 1: Verify `extractSymbolsSplit()` returns tree, verify tree reuse produces identical scope bindings
   - Phase 2: Verify `resolveImportTargetLocal()` matches `resolveImportTarget()` for known paths
   - Phase 3: Verify batch reindex produces same DB state as sequential per-file reindex
   - Phase 4: Verify separated computation produces identical edge sets
2. **Benchmark comparisons** before/after for repos with 200, 500, and 1000+ files
3. **Memory profiling** to ensure retained trees (Phase 1) are properly deleted
4. **Integration test** with real large repository

## Risk Assessment

- **Phase 1 (Low risk):** Tree reuse is transparent — same tree, same results. Must ensure `tree.delete()` is called in all code paths.
- **Phase 2 (Low risk):** Replacing SQL queries with Map lookups produces identical results. The Map is built from the same data that the SQL queries would return.
- **Phase 3 (Medium risk):** Refactoring reindex to batch mode changes transaction boundaries. Must verify that partial failures (e.g., one file fails to parse) don't corrupt the batch.
- **Phase 4 (Low risk):** Separating computation from writes doesn't change results, only ordering of operations.
