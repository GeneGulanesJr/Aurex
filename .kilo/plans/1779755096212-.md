## Phase 2 — Mission Tables

### Issue 2.1: Mission & Milestone Tables
**Labels**: `phase-2`, `schema`

Design and implement migration for `missions` and `milestones` tables in the LaPis SQLite DB.

**`missions` table**:
```sql
CREATE TABLE IF NOT EXISTS missions (
  id TEXT PRIMARY KEY,                -- UUID
  description TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'planning',  -- planning|running|paused|complete|failed
  plan_json TEXT,                     -- full plan from Planner
  config_json TEXT,                   -- runtime config (timeouts, limits)
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  completed_at TEXT
);
```

**`milestones` table**:
```sql
CREATE TABLE IF NOT EXISTS milestones (
  id TEXT PRIMARY KEY,                -- UUID
  mission_id TEXT NOT NULL REFERENCES missions(id),
  seq INTEGER NOT NULL,               -- ordering within mission
  title TEXT NOT NULL,
  description TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'pending',  -- pending|in_progress|validating|passed|failed|rescoped
  validation_contracts_json TEXT NOT NULL,  -- array of contracts
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at TEXT NOT NULL DEFAULT (datetime('now')),
  completed_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_milestones_mission ON milestones(mission_id);
```

Migration runs on backend startup via `better-sqlite3` or `@libsql/client` against the configured DB path. Uses `PRAGMA user_version` to track applied migrations (LaPis uses versions 1-10; Aurex starts at version 100 to avoid conflicts). All migrations are additive — never modify LaPis's existing tables.

**Dependencies**: Issue 1.1  
**Acceptance**: Backend startup creates `missions` and `milestones` tables in the LaPis DB without touching existing tables. Re-running startup is idempotent.

### Issue 2.6: Migration Runner
**Labels**: `phase-2`, `infra`

Implement a migration runner in the backend that:

1. Opens the LaPis SQLite DB at the configured path
2. Checks `PRAGMA user_version` — if < 100, Aurex hasn't migrated yet
3. Runs all Aurex migrations (issues 2.1-2.5) sequentially within a transaction
4. Sets `PRAGMA user_version = 100 + N` where N is the number of Aurex migrations
5. On subsequent startups, only runs new migrations
6. Each migration is a separate SQL file in `packages/backend/src/migrations/`
7. Never modifies LaPis's existing tables or their `user_version` scheme

**Dependencies**: Issues 2.1–2.5  
**Acceptance**: Backend startup runs migrations idempotently. LaPis's existing tables and data are untouched.

### Issue 3.2: LaPis Memory Integration Points
**Labels**: `phase-3`, `lapis-client`

Define when and how the Orchestrator uses LaPis memory:

1. **Mission Start**: Call `saveMemory` to record the mission description and plan as a LaPis observation of type `mission_plan`. This lets future missions search for past decisions.
2. **Worker Handoff**: After a worker completes, call `saveMemory` with the handoff rationale and assumptions as type `implementation_decision`.
3. **Milestone Complete**: Call `saveMemory` with the milestone outcome as type `milestone_result`.
4. **Mission Complete**: Call `saveMemory` with the full mission summary as type `mission_summary`.
5. **Mission Start (recall)**: Call `searchMemory` with the mission description to find relevant past decisions, patterns, and bugfixes. Inject these into the Planner's context.

These calls are made from the Orchestrator modules (Phase 5), not from the LaPis client itself. This issue defines the integration contract.

**Dependencies**: Issue 3.1  
**Acceptance**: Integration points are documented and the shared types package includes the memory integration schemas.

The Orchestrator **never** calls any LLM directly — always through this client.

## Phase 5 — Orchestrator

### Issue 5.1: Planner Module
**Labels**: `phase-5`, `orchestrator`

Implement `packages/backend/src/orchestrator/planner.ts`:

1. Accepts a mission description (string) from the REST API
2. Calls LaPis `searchMemory` to find relevant past decisions, patterns, and bugfixes
3. Calls Router `planningCall` with the mission description + relevant memories as context
4. Receives structured milestone plan and validation contracts
5. Writes to SQLite:
   - A `missions` row with the description and plan
   - One `milestones` row per planned milestone with validation contracts
   - Working units are derived from milestones and written to `working_units`
6. Calls LaPis `saveMemory` to record the mission plan
7. Returns the mission ID and full plan to the caller
8. Enforces a maximum milestone count (configurable, default 10) to prevent runaway plans

**Dependencies**: Issues 3.1, 4.1, 2.1  
**Acceptance**: Given a mission description, produces a persisted mission with milestones, working units, and validation contracts. Relevant memories are included in planning context.

---

### Issue 5.2: Overlap Module
**Labels**: `phase-5`, `orchestrator`

Implement `packages/backend/src/orchestrator/overlap.ts` — pure logic, no LLM calls:

1. Reads all working units for a milestone from SQLite
2. Each working unit declares `file_paths_json` and `modules_json` — the files and modules it will touch
3. Builds a conflict graph: two working units conflict if they share any file path or module
4. Computes which working units can run concurrently vs serially:
   - Units with zero overlap → run in parallel
   - Units with overlap → run serially (ordered by declared dependency if any)
5. Returns a **serialization map**:
   ```typescript
   interface SerializationMap {
     batches: WorkingUnitBatch[];
   }
   interface WorkingUnitBatch {
     batchIndex: number;
     unitIds: string[];  // these run in parallel
     dependsOnBatches: number[];  // must wait for these batches
   }
   ```
6. Logs the serialization map to the mission's broadcast table as an `info` broadcast

**Dependencies**: Issue 2.2  
**Acceptance**: Given working units with declared file paths and modules, produces a correct serialization map. Units with zero overlap are in the same batch. Units with overlap are in different batches with dependency edges.

---

### Issue 5.3: Milestone Loop Module
**Labels**: `phase-5`, `orchestrator`

Implement `packages/backend/src/orchestrator/milestone-loop.ts` — the main execution loop:

1. For each milestone in sequence:
   a. Read working units from SQLite
   b. Call Overlap module to get serialization map
   c. Emit `milestone_started` WebSocket event
   d. For each batch in the serialization map:
      - Spawn Pi instances as child processes for each working unit in the batch (via Pi Spawn Layer, Phase 6)
      - Emit `worker_spawned` events
      - Monitor for handoff writes in SQLite (poll or watch)
      - When all workers in batch complete, emit `worker_completed` events
   e. After all batches complete, spawn Validator pair (two Pi instances: one reads working unit changes, one reads validation contracts)
   f. Collect validator verdicts from SQLite
   g. Pass verdicts to Negotiator module
   h. Act on Negotiator's decision:
      - `pass` → mark milestone as passed, move to next
      - `retry` → increment retry counter, re-run failed working units (up to max)
      - `rescope` → check rescope count, if under limit, re-plan milestone via Planner with rescoped context; if over limit, emit checkpoint event
      - `escalate` → emit checkpoint event for human decision
   i. Enforce per-task-type timeouts (configurable in `missions.config_json`)
   j. On timeout, kill Pi process, write timeout event to `retry_counters`
   k. Emit broadcasts for significant events (batch started, batch completed, validation started, etc.)
2. After all milestones complete, mark mission as complete
3. Call LaPis `saveMemory` with mission summary

**Dependencies**: Issues 5.1, 5.2, 5.4, 6.1  
**Acceptance**: Can run through a milestone with one batch of one working unit, collect handoff, spawn validators, get negotiator verdict, and advance. Timeout and retry logic works.

---

### Issue 5.4: Negotiator Module
**Labels**: `phase-5`, `orchestrator`

Implement `packages/backend/src/orchestrator/negotiator.ts`:

1. Takes handoffs and validator verdicts for a milestone
2. Calls Router `planningCall` with structured input:
   - System prompt: "You are a code review negotiator. Given the worker handoffs and validator verdicts, decide the next action."
   - User prompt includes: milestone description, validation contracts, worker handoffs (rationale + files modified), validator findings, previous retry count
3. Receives structured decision:
   ```typescript
   interface NegotiatorDecision {
     verdict: 'pass' | 'retry' | 'rescope' | 'escalate';
     reasoning: string;
     rescopedSpec?: string;  // only for 'rescope'
     retryUnits?: string[];  // working unit IDs to retry, only for 'retry'
   }
   ```
4. Writes decision to `broadcasts` table as a `decision` broadcast
5. If `rescope`, writes a `rescope_history` entry
6. Returns decision to Milestone Loop

**Dependencies**: Issues 4.1, 2.3, 2.4  
**Acceptance**: Given handoffs and validator verdicts, produces a typed decision. Pass/retry/rescope/escalate paths all work. Decisions are persisted to SQLite.

### Issue 6.2: Handoff Schema Validation
**Labels**: `phase-6`, `spawn-layer`

Implement handoff acceptance/rejection logic:

1. When a Worker Pi process exits, read the handoff from its output (or from a well-known file path in the workspace)
2. Validate the handoff against required schema:
   - `rationale` — non-empty string explaining why changes were made
   - `assumptions` — non-empty array of assumptions made during implementation
   - `files_modified` — array of file paths modified
   - `summary` — brief summary of what was done
3. If validation passes:
   - Write handoff to `handoffs` table with status `pending`
   - Update `working_units` status to `completed`
4. If validation fails (missing rationale or assumptions):
   - Reject the handoff
   - Update `working_units` status to `rejected`
   - Write rejection broadcast
   - Increment retry counter
5. Emit WebSocket events for both acceptance and rejection

**Dependencies**: Issues 6.1, 2.3  
**Acceptance**: Complete handoffs with rationale and assumptions are accepted. Incomplete handoffs are rejected with clear error messages. Both paths are persisted in SQLite and emit WebSocket events.

### Issue 6.3: Validator Pair Spawner
**Labels**: `phase-6`, `spawn-layer`

Implement the Validator pair spawning logic:

1. After all Workers in a milestone complete (all handoffs accepted):
   a. **Validator A** (Implementation Reviewer): Gets the handoffs and modified files, reviews code quality and correctness
   b. **Validator B** (Contract Checker): Gets the validation contracts and modified files, checks if contracts are satisfied
2. Both validators run in parallel as separate Pi processes
3. Each validator writes its findings to `research_findings` with `source = 'validator'`
4. Each validator produces a verdict: `pass` or `fail` with reasons
5. Validator findings are collected and passed to the Negotiator
6. If either validator times out, the milestone is marked as needing human review (checkpoint event)

**Dependencies**: Issues 6.1, 2.4  
**Acceptance**: Two validator Pi processes spawn in parallel, each with distinct roles. Both produce findings. Timeouts trigger checkpoint events.

**`POST /missions`** — Create and start a mission:
- Body: `{ description: string }`
- Calls Planner module to create mission plan
- Returns `{ missionId: string, plan: MissionPlan }` with status `201`
- Starts the Milestone Loop asynchronously (does not block the response)

**`POST /missions/:id/checkpoint`** — Submit human checkpoint decision:
- Body: `{ decision: 'approve' | 'reject' | 'override', overrideReason?: string, revisedSpec?: string }`
- Resolves the pending checkpoint in the Milestone Loop
- Returns `{ accepted: true }` with status `200`
- Returns `404` if mission not found or no pending checkpoint
- Returns `409` if checkpoint already resolved

**`GET /missions/:id`** — Get current mission state:
- Returns full mission state: status, current milestone, active workers, recent broadcasts, cost totals, retry counts
- Returns `404` if mission not found

**`GET /missions`** — List all missions (paginated):
- Query params: `status`, `limit`, `offset`
- Returns array of mission summaries

**Dependencies**: Issues 7.1, 5.1  
**Acceptance**: Can create a mission, get its state, and submit checkpoint decisions. All error cases return appropriate status codes.

### Issue 7.3: WebSocket Live Events
**Labels**: `phase-7`, `backend`

Implement WebSocket on `/ws/:missionId`:

1. Clients connect to follow a specific mission's live event stream
2. Events pushed to clients:
   - `mission_started` — mission begins execution

   - `worker_spawned` — a Pi Worker is spawned (includes unit ID, title)

   - `milestone_completed` — milestone passes
   - `milestone_failed` — milestone fails
   - `mission_completed` — all milestones done
   - `mission_failed` — mission terminates with failure
   - `cost_update` — new cost entry recorded
3. Events are typed using shared package types
4. Multiple clients can connect to the same mission
5. Server handles client disconnection gracefully
6. On reconnect, client can request missed events via REST (future: event replay from SQLite)

## Open Questions (to resolve during implementation)

1. **Pi RPC Interface**: How exactly to spawn Pi as a child process with a task spec. The Pi Spawn Layer (Phase 6) assumes an interface — this needs to be validated against the actual Pi binary.
2. **Pi Installation in Docker**: How Pi gets installed in the backend Docker image. Options: download binary, build from source, or mount from host.
3. **Concurrent Mission Support**: The initial plan supports one mission at a time. Multi-mission support requires process isolation and resource limits — deferred to a future phase.
4. **WebSocket Event Replay**: On reconnect, should the server replay missed events? This requires event persistence beyond SQLite — deferred to a future phase.
5. **Authentication**: No auth between frontend and backend (localhost/Docker network only). If exposed externally, add auth in a future phase.
