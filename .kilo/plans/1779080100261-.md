# Plan: Fix Call Graph Builder Scalability on Large Repositories

## Root Cause Analysis

The `buildCallGraph` function in `src/code-analysis/legacy-core.js:307-617` has a critical **O(symbols × files)** complexity bug:

### Bug 1: Repeated Full-File AST Parsing (PRIMARY CAUSE)

```
legacy-core.js:549-614 — for each symbol:
  extractFn(sym.file_path, sym.file_content)   ← parses ENTIRE file
  astCallees = allCallees.filter(line range)    ← then discards most results
```

If a file has 50 exported functions, the entire file is AST-parsed **50 times** — once per symbol — only to filter down to callees within that symbol's line range each time. For a repo with 1000 files × 50 symbols = **50,000 full-file AST parses** instead of 1,000.

### Bug 2: All File Contents Duplicated Per Symbol

```
legacy-core.js:318-324 — SELECT ... cf.content as file_content
  FROM code_symbols cs JOIN code_files cf ...
```

This join duplicates every file's full text once per symbol in that file. A 20KB file with 50 symbols creates 1MB of duplicate strings in the result set. For large repos this causes OOM.

### Bug 3: No Progress Reporting

`buildCallGraph` is a single synchronous function with no callbacks. The caller (`rebuildDerivedIndexes` in `incremental-indexer.js:92`) emits "Building call graph..." once, then blocks until completion — which can be minutes/hours on large repos with no visible progress.

### Bug 4: No Resource Limits or Timeouts

No configurable limits on memory, time, or symbol count. A runaway repo simply hangs.

## Proposed Changes

### 1. Invert the Loop — Parse Each File Once (CRITICAL FIX)

**File: `src/code-analysis/legacy-core.js` — `buildCallGraph` function (lines 307-617)**

Replace the symbol-centric loop with a file-centric approach:

```
BEFORE (current):
  for each symbol:
    parse entire file → filter callees to symbol's line range → resolve

AFTER (proposed):
  1. Group symbols by file_id
  2. For each file:
     a. Parse file once → get ALL callees with line numbers
     b. For each callee, find which symbol(s) contain that line
     c. Resolve callee → insert edge
```

This reduces complexity from O(symbols × file_parse_cost) to O(files × file_parse_cost).

Implementation approach:
- Query `code_symbols` grouped by `file_id` with line ranges (no file content join)
- Query `code_files` separately, only storing content in a bounded LRU cache
- Parse each file's content once via `extractCalleesFromContent`
- Build a line-interval index per file to dispatch callees to their enclosing symbols
- Process regex fallback per-symbol but only on the symbol body (already extracted from the single file parse)

### 2. Fix Memory — Separate File Content Loading

**File: `src/code-analysis/legacy-core.js`**

- Split the initial query into two:
  1. `SELECT ... FROM code_symbols WHERE repo_id = ?` (no file content join)
  2. Load file contents on-demand in file-centric loop, one at a time
- Keep the in-memory symbol indexes (`symbolsByName`, `symbolsByQualified`, etc.) — they're necessary for O(1) callee resolution
- Remove `file_content` from the symbols query result

### 3. Add Batched Progress Reporting

**File: `src/code-analysis/legacy-core.js` — `buildCallGraph` function**

Add an optional `onProgress` callback parameter:

```js
function buildCallGraph(db, repoId, opts = {}) {
  const { onProgress } = opts;
  // ... 
  let processedFiles = 0;
  for (const [fileId, fileSymbols] of symbolsByFile) {
    // ... process file ...
    processedFiles++;
    if (onProgress && processedFiles % 50 === 0) {
      onProgress({ filesProcessed: processedFiles, totalFiles, callsFound: totalCalls });
    }
  }
}
```

**File: `src/code-index/incremental-indexer.js` — `rebuildDerivedIndexes` function (lines 79-108)**

Thread through a progress callback so "Building call graph..." includes file counts:

```js
const cg = buildCallEdges(db, repoId, { onProgress: (p) => {
  emitProgress(args, 'analysis', { message: `Building call graph... ${p.filesProcessed}/${p.totalFiles} files, ${p.callsFound} calls` }, stats);
}});
```

### 4. Add Configurable Limits

**File: `constants.js`**

Add a new `CALL_GRAPH` constant section:

```js
const CALL_GRAPH = {
  MAX_SYMBOLS_PER_FILE: 5000,    // warn if exceeded
  MAX_FILE_CONTENT_BYTES: 2_000_000,  // skip files > 2MB for AST parsing (regex fallback)
  PROGRESS_INTERVAL_FILES: 50,
};
```

**File: `src/code-analysis/legacy-core.js`**

- Skip AST parsing for files exceeding `MAX_FILE_CONTENT_BYTES`, fall back to regex per-symbol
- Emit a warning (via onProgress) for files with > `MAX_SYMBOLS_PER_FILE` symbols

### 5. Thread opts Through the Call Chain

The following files need minor signature changes to thread the `opts` parameter:

- `src/code-index/edge-extractor.js:7` — `buildCallEdges(db, repoId, opts)`
- `src/code-analysis/graph.js:18-19` — `analyzeBuildCallGraph(db, repoId, opts)` 
- `src/code-index/incremental-indexer.js:93-94` — pass progress callback to `buildCallEdges`

All changes are backward-compatible (opts defaults to `{}`).

## Risk Assessment

- **Low risk**: The output of `buildCallGraph` (inserts into `code_calls` table) is unchanged — same schema, same data
- **Medium risk**: The file-centric grouping needs careful handling of edge cases (symbols with no file, overlapping line ranges, symbols spanning entire files)
