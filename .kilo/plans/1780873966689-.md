# Fix: Missions Constant Rescoping & Shallow Initial Planning

## Root Cause Analysis

After investigation, there are **three interconnected problems** causing the constant-rescoping behavior:

### Problem 1: Rescope prompt is shallow and blind (`rescope.ts`)

The rescope function re-plans a milestone with almost no context:

```
"You are a mission planner. Re-plan this milestone given the validation failures."
```

The user message only includes: milestone title, description, a short failure reason string, and mission description. It does **NOT** receive:
- Validator's detailed findings (what specifically failed and why)
- Worker handoff data (what was actually attempted)
- Research findings (codebase knowledge gathered by the research agent)
- Previous attempt history

So the rescope is re-planning blind — it generates similar bad units, fails again, and loops.

### Problem 2: Initial planner lacks codebase context (`planner.ts` + `mission-runner.ts`)

The mission runner **indexes the repo** (`lapis.indexRepo`, `lapis.getCodeSummary`) before calling the planner, but the planner **never receives** the indexed data. It only searches `lapis.searchMemory`, which is semantic search over stored memories, NOT the actual codebase structure. This means milestones are planned without knowledge of:
- Actual file/directory structure
- Existing modules and their relationships
- Symbols, entry points, dependency cycles

This produces milestones with wrong `declaredPaths`, missing dependencies, and unrealistic scope — which causes validation failures, which triggers rescoping.

### Problem 3: Research findings are written but never consumed

The research agent runs in the milestone loop (lines 292-328 of `milestone-loop.ts`) and writes findings via `writeFinding`, but:
- **Workers** never read findings (`buildWorkerContext` doesn't include them)
- **Validators** never read findings (`buildValidatorContext` doesn't include them)
- **Rescope** never reads findings (only gets a short reason string)

The entire research phase is wasted. Agents work without the knowledge the research agent gathered.

---

## Plan

### Step 1: Enrich the planner with indexed codebase context

**Files**: `planner.ts`, `mission-runner.ts`

- In `mission-runner.ts`, after indexing the repo, pass the `codeSummary` to the planner
- In `planner.ts`, add an optional `codeSummary` parameter to `createPlanner`
- Include in the planner's system prompt:
  - Module list with file counts
  - Entry points
  - Key file paths
  - Dependency cycles
- This lets the LLM plan milestones with correct `declaredPaths` and `declaredModules`

### Step 2: Feed research findings into subsequent phases

**Files**: `milestone-loop.ts`, `context-builder.ts`, `rescope.ts`

- After the research phase completes, call `lapis.getFindings(mission.id)` to retrieve findings
- Pass findings into:
  1. **Worker context** (`buildWorkerContext`) — workers know patterns/structures
  2. **Validator context** (`buildValidatorContext`) — validators can verify against research
  3. **Rescope prompt** (`rescopeMilestone`) — re-planning is informed by discoveries

### Step 3: Enrich the rescope prompt with failure context

**Files**: `rescope.ts`, `milestone-loop.ts`

- Expand `RescopeInput` to include:
  - Validator verdicts (findings, classification, failed unit IDs)
  - Worker handoff summaries (what was attempted, what succeeded, what failed)
  - Research findings gathered so far
  - Attempt history (how many retries/rescopes, what changed)
- Rewrite the rescope system prompt to use all this context for informed re-planning
- The rescope should understand *why* the previous plan failed before generating a new one

### Step 4: Make rescope trigger smarter

**Files**: `milestone-loop.ts`

Currently, the flow is: workers → research → validators → negotiate. If negotiate says "rescope", it rescopes immediately. Changes:
- After rescope, carry forward completed/successful units (don't re-plan what worked)
- Include a summary of what was achieved vs what failed in the rescope context
- This ensures rescoping only re-plans the failing parts, not the entire milestone

### Step 5: Update tests

**Files**: `rescope.test.ts`, `milestone-loop.test.ts`, `planner.test.ts`, `negotiator.test.ts`

- Update `rescope.test.ts` to verify enriched context is passed to the LLM
- Update `milestone-loop.test.ts` to verify findings are fetched and passed through
- Update `planner.test.ts` to verify codebase context is included in the prompt
- Add test for rescope carrying forward successful units

---

## Priority Order

1. **Step 1** (planner enrichment) — fixes the root cause of bad initial plans
2. **Step 3** (enriched rescope) — fixes the immediate "blind rescope" problem
3. **Step 2** (research findings propagation) — ensures research is useful
4. **Step 4** (smarter rescope trigger) — prevents re-planning successful work
5. **Step 5** (tests) — verify everything works
