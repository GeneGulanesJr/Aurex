Scope: `packages/backend`, `packages/frontend`, `packages/shared`. Entry points traced: `server.ts` (backend), `App.tsx` ← `main.tsx` (frontend). All findings below were verified by grep + cross-reference (a symbol counts as dead only if it has **zero** non-test, non-definition callers).

> Methodology note: every candidate was checked against production source AND tests. Findings are grouped by the requested categories and ordered by runtime-impact severity (silent failures first).

## Category 1 — STUB / PLACEHOLDER IMPLEMENTATIONS

### 1.1 Durable "agent launcher" is a deliberate stub that throws
- **Location:** `packages/backend/src/sessions/prepared-session-service.ts:219-230` (handler), `:195-292` (factory)
- **What it's supposed to do:** `createPreparedSessionStartHandler` should drive a prepared agent session `starting → running (heartbeats) → completed/failed` by invoking a real `launchAgent` callback that spawns an actual agent process.
- **Why it's broken:** `server.ts:230-235` constructs `createMissionQueueHandlers({ pool, sessions, queue, messages })` with **no `launchAgent`**. So when an `agent_session_start` / `agent_session_resume` job runs, the handler explicitly calls `sessions.fail(...)` with *"Agent launcher not wired"* and throws. The entire session-launch code path (`markRunning`/`heartbeat`/`waitForInput`/`drainMessages`) in lines 242-291 is therefore **unreachable** in production.
- **Severity:** High — this is the single largest half-built feature. The fallback message even tells operators to "Enable `AUREX_DURABLE_QUEUE_ENABLED=false`".
- **Fix / next step:** Either (a) finish wiring a concrete `LaunchAgent` (e.g. adapt `agent-spawner.ts` into a launcher), or (b) mark the subsystem explicitly experimental and remove the dead session-lifecycle body until then.

## Category 3 — INCOMPLETE WIRING

### 3.1 Durable execution queue + prepared sessions + stale reconciler: gated off AND unlaunched
- **Location:** `server.ts:225-253`, `config.ts:114-125`, `prepared-session-service.ts:227`
- **What it's supposed to do:** Queue-backed mission/session dispatch, durable prepared agent sessions, and automatic stale-session reconciliation.
- **Why it's broken:** All three are gated behind `AUREX_DURABLE_QUEUE_ENABLED`, `AUREX_PREPARED_SESSIONS_ENABLED`, `AUREX_STALE_RECONCILER_ENABLED` which default to `false`. Even when flipped on, **no `launchAgent` is registered** (see 1.1), so prepared sessions fail at start. `docs/api.md:321-323` labels these flags *"Reserved"*. `docs/superpowers/plans/2026-06-11-prepared-sessions-durable-queue.md:646` says *"Keep default false until integration tests pass."*
- **Severity:** High (silent feature gap). The queue worker, stale reconciler, and `agent-sessions` / `execution-queue` REST routes are effectively dormant.
- **Fix / next step:** Finish the launcher (1.1), add integration tests, then flip the default. Until then, surface a clearer "experimental" status in the UI/docs.

### 3.3 Enforcement gates are defined but never applied to real transitions
- **Location:** `enforcement/enforcement-gate.ts`, `broadcast-lifecycle.ts`, `research-lifecycle.ts` (see Category 2)
- **What it's supposed to do:** Validate `BroadcastLifecycle` / `ResearchLifecycle` state transitions (e.g. prevent an `active` broadcast from being superseded by the wrong actor).
- **Why broken:** `lapis-client.ts:110-116` exposes `transitionBroadcast` / `transitionFinding`, which are the methods actually used — but they bypass `enforcement-gate`. So the transition rules exist and are unit-tested, yet **no production transition is ever validated by them**. This is a silent enforcement gap rather than a crash.
- **Severity:** Medium (guardrail that doesn't guard).
- **Fix / next step:** Either call `enforceBroadcastTransition`/`enforceResearchTransition` from inside the `lapis-client` transition methods (or the orchestrator callers), or delete the modules if enforcement is intentionally deferred.

### 3.4 `researchTimeout` config is parsed but never consumed
- **Location:** `config.ts:93` (and `AppConfig.researchTimeout:12`)
- **Why broken:** `RESEARCH_TIMEOUT` (documented in README + `.env.example`, default 120000ms) is read into config and asserted in `config.test.ts`, but **no production code ever reads `config.researchTimeout`**. The research agent (tools exist in `agents/research-tools.ts`, imported by `agent-spawner.ts`) therefore runs without this timeout being enforced.
- **Severity:** Medium — a documented timeout that silently does nothing.
- **Fix / next step:** Wire `researchTimeout` into the research-agent spawn path, or remove the config field + env var.

## Corrected understanding (verified)
- **Findings are half-wired.** `writeFinding` (research-tools.ts:48) creates findings as `unverified`; `getFindings` (milestone-loop.ts:145,230; checkpoint-loop.ts:98) reads them into worker/validator/checkpoint context. But `transitionFinding` (lapis-client.ts:453) is **never called** → findings are created `unverified`, consumed, and never move to `verified`/`rejected`/`expired`. The enforcement gate `enforceResearchTransition` validates a transition that never occurs.
- **Broadcasts are entirely unbuilt.** `getBroadcasts`/`transitionBroadcast`/`createBroadcast` have **zero production callers**. The `Broadcast`/`BroadcastLifecycle` subsystem (client methods + `enforceBroadcastTransition` + `broadcast-lifecycle.ts`) exists only in tests.
- **Both research AND validator timeouts are dead config.** `config.researchTimeout` (`RESEARCH_TIMEOUT`) AND `config.validatorTimeout` (`VALIDATOR_TIMEOUT`) are parsed (config.ts:92-93) but never consumed. Both spawns hardcode `config.workerTimeouts.testHeavy`:
  - research spawn: `milestone-loop.ts:214`
  - validator spawn: `milestone-loop.ts:802`

Therefore the work splits into **3 tiers** of increasing scope/risk. Tier 1 is mechanical; Tier 2 implements the missing lifecycle (needs one product decision); Tier 3 is a separate call.

## TIER 1 — Wire the agent timeouts (clean, mechanical)  [3.4 + newly-found validatorTimeout]

**Problem:** both dedicated timeouts are ignored; research + validator agents use the `testHeavy` (600s) worker timeout regardless of the documented values.

**Changes:**

2. `packages/backend/src/orchestrator/milestone-loop.ts:802` → change to `timeout: config.validatorTimeout`.

4. **Tests:** add cases in `__tests__/milestone-loop-spawn.test.ts` asserting the spawn `timeout` passed to the spawner equals the configured research/validator timeout (mirror the existing `timeout_disabled` assertions at lines 424/484/541).

**Risk:** Low. Behavior change only if an operator has set `RESEARCH_TIMEOUT`/`VALIDATOR_TIMEOUT` to something other than the default (defaults match the prior hardcoded... actually defaults are 120s/180s vs hardcoded 600s — so this **will** shorten research/validator runtimes to their documented caps). ## TIER 2 — Wire the findings lifecycle + make the research enforcement gate live (3.3, partial)  [needs 1 product decision — see question]

**Goal:** findings currently live forever as `unverified`. Implement the `verified`/`rejected` transition path so `enforceResearchTransition` actually guards something, and so workers' standing-check context reflects real verification.

**Intended design (grounds the gate):** research-tools.ts:65 says findings *"will be verified by Workers when they encounter the matching domain."* So verification is **worker-driven**.

**Changes:**
1. **New worker tools** in `packages/backend/src/agents/worker-tools.ts`:
   - `verify_finding({ findingId })` → calls `lapis.transitionFinding(findingId, "verified", workerAuthorId, { taskId, workerSessionId })`, but **first** guarded by `enforceResearchTransition(currentStatus, "verified", actorId, standingContext)`. Read current status via a new `lapis.getFinding(id)` (or reuse `getFindings` filter). On `ok:false`, return the rejection reason to the worker instead of mutating state.
   - `reject_finding({ findingId, reason })` → same pattern targeting `"rejected"`.
   - Populate `StandingContext = { taskId, workerSessionId }` from the worker's active unit + session id (already available in the spawn context).
2. **Wire enforcement module:** `enforcement/enforcement-gate.ts` becomes a real production import (currently test-only). This also un-deads `research-lifecycle.ts`'s `canTransitionFinding`.
3. **Skill docs:** update `packages/backend/src/skills/worker.md` to instruct workers to call `verify_finding`/`reject_finding` when they act on a domain finding.
4. **Tests:** new `__tests__/worker-finding-tools.test.ts` covering: verify a genuinely `unverified` finding (passes); verify an already-`verified`/`expired` finding (gate rejects, state unchanged); reject path; missing standingContext rejected.

**Product decision (LOCKED):** verification is **worker-initiated via tool calls** (`verify_finding`/`reject_finding`) — matches the existing skill comment and is the smaller change. NOT orchestrator-auto-verify.

**Out of scope for Tier 2:** finding **expiration** (`superseded`/`expired` via TTL). `writeFinding` sets `ttl:null, expiresAt:null` today; adding a TTL sweep is a separate enhancement (could reuse the stale-reconciler pattern) and is not required to make the gate live. **Also out of scope: any Broadcast code** (deferred to Tier 3 follow-up).
