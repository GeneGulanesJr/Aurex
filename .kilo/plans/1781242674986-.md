# PR #94 Review: Worker activity-aware timeouts, handoff validation, and milestone spawn behavior

## Summary

This PR adds three capabilities to the worker agent lifecycle:
1. **Activity-aware idle timeouts** — tool/cost activity refreshes the idle window, bounded by a configurable `maxTimeout`
2. **Worker handoff enforcement** — worker sessions that end without an accepted `write_handoff` are failed
3. **Failure classification** — the milestone loop distinguishes timeout vs handoff failures for retry/escalation decisions

Overall the design is sound and the test coverage is good. There are a few issues that should be addressed before merge.

---

## Issues

### CRITICAL

#### 1. Full tool results logged and exposed via agent-log API (`agent-spawner.ts:~296`)

The `tool_execution_end` handler logs `event.result` directly:
```ts
data: { tool: event.toolName, isError: event.isError, result: event.result },
```

`event.result` can contain command stdout/stderr, file contents, grep output, or other sensitive data. The agent-log API returns `data` to clients, so this leaks secrets/PII. Log a redacted summary or explicit safe fields (e.g., `resultLength`, `isError`, `truncated`) instead of the full result.

### WARNING

#### 2. `workerTimeouts` is accessed without null/undefined guard (`milestone-loop.ts:314`)

`selectWorkerTimeout` receives `config.workerTimeouts` and accesses `.testHeavy`, `.build`, `.simple` without checking if it's defined. If a mission doesn't set `workerTimeouts` in its `configJson`, this throws a runtime TypeError, crashing the milestone loop.

**Fix:** Add a default fallback, e.g.:
```ts
const timeouts = workerTimeouts ?? { simple: 300_000, build: 600_000, testHeavy: 600_000 };
```
Or guard at the call site in the milestone loop before invoking `selectWorkerTimeout`.

#### 3. Tool execution ID fallback can collide (`agent-spawner.ts:~285`)

When `toolCallId` is not a string, the fallback ID is `${event.toolName}:${Date.now()}`. Concurrent tool executions without string `toolCallId` values can reuse the same ID in the same millisecond, causing the `activeToolExecutions` set to undercount. This leads to premature timeouts or stale active-tool state.

**Fix:** Use a monotonically increasing counter:
```ts
let toolExecCounter = 0;
// ...
const id = typeof event.toolCallId === "string" ? event.toolCallId : `${event.toolName ?? "tool"}:${++toolExecCounter}`;
```

#### 4. Contract-level `testCommands` make all units classify as `testHeavy` (`milestone-loop.ts:~1079`)

`selectWorkerTimeout` concatenates `testCommands` (milestone-level contract commands) with unit-level text. A generic command like `npm test` matches every worker unit, forcing all units into the `testHeavy` bucket and defeating the per-unit timeout selection.

**Fix:** Only include `testCommands` in the regex text if the unit's own description/paths already hint at test work, or remove `testCommands` from the classification text and rely solely on unit-level signals.

#### 5. `activeToolExecutions` entries leak for fallback IDs (`agent-spawner.ts`)

When `tool_execution_start` creates a fallback ID (non-string `toolCallId`), the corresponding `tool_execution_end` won't delete it because the delete only runs when `typeof event.toolCallId === "string"`. These phantom entries keep the set non-empty, causing `fireTimeout` to keep extending the timeout even after tools finish.

**Fix:** Track fallback IDs consistently — either use the same ID generation logic on end events, or use the counter-based approach from issue #3 and always delete.

### SUGGESTION

#### 6. `refreshTimeoutOnActivity` logs are very noisy (`agent-spawner.ts`)

Every tool call, usage update, and `tool_execution_*` event emits a `config_decision` log. In an active session this can generate hundreds of log entries, drowning out genuinely interesting config decisions.

**Fix:** Throttle the extension log (e.g., log at most once per N seconds, or only when the extension changes the scheduled timeout by more than a threshold). Keep the actual rescheduling behavior as-is.

#### 7. `selectWorkerMaxTimeout` formula may produce very large timeouts for large base timeouts (`milestone-loop.ts`)

`Math.max(timeout * 4, timeout + 10 * 60_000)`: for a 600s base timeout, maxTimeout is 2400s (40 minutes). Consider whether this is appropriate, or cap at an absolute maximum.

---

## What looks good

- The `failSession` path and `settled` guard are clean and prevent double-resolution.
- The `fireTimeout` → `scheduleTimeout` rescheduling loop with `maxTimeout` bounding is correct.
- Handoff enforcement via `workerHandoffRequired` / `workerHandoffAccepted` is a good pattern — it's defensive (only enforced when the `write_handoff` tool is actually registered).
- The milestone loop failure classification (`timeoutFailureUnitIds` / `handoffFailureUnitIds`) gives clear escalation summaries.
- Test coverage is solid — new test file for worker lifecycle, updated existing tests for timeout extension and handoff scenarios.

## Recommendation

**Address issues #1 (critical) and #2–#5 (warnings) before merge.** Issues #6–#7 are suggestions for follow-up.
