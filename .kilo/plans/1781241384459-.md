# PR #93 Review: Persistent Data Volumes + In-App Self-Update System

## Summary of PR
The PR adds (1) a `lapis-data` named Docker volume for persistence across rebuilds, (2) an in-app self-update system with daily git checks + WebSocket notifications, and (3) a cron-based flag-file approach for safe container rebuilds.

## Issues Found

### Critical

1. **`.kilo/plans/` file committed in PR** — `.kilo/plans/1781217897555-.md` is a development artifact that should be removed from the PR diff entirely.

2. **Unused import `access`** in `packages/backend/src/routes/update.ts:3`:
   ```ts
   import { writeFile, access } from "fs/promises";
   ```
   `access` is never used. Should remove it.

3. **`cron-update.sh` has no concurrency protection** — Cron runs every minute. If `docker compose up --build -d` takes longer than 1 minute (common for large images), two concurrent runs will race. Fix: add `flock`-based locking.

4. **Health check polling won't work in dev mode** — `useUpdateStatus.ts:62` uses bare `fetch("/health")`, but `vite.config.ts` only proxies `/api` and `/ws`, not `/health`. The production `nginx.conf` does proxy `/health`, so this only affects dev. Fix: add `/health` to the vite dev proxy.

### Medium

5. **`behindBy` fallback of `1` on git log failure** in `update.ts:80`:
   ```ts
   behindBy = logCount ? logCount.split("\n").filter(Boolean).length : 1;
   ```
   If `git log` fails (e.g., shallow clone, network issue), `behindBy` becomes `1` even though we don't know the actual count. The `updateAvailable` flag is already `true`, so the user will see the notification. The `1` is misleading. Should use `0` or omit the field, since `updateAvailable: true` is sufficient.

6. **`captureBuildSha()` is fire-and-forget** at module level (`update.ts:89`). While the `/api/update/status` handler has a fallback (`if (!currentSha) await captureBuildSha()`), this means the first request after startup may block on git. Not a bug, but the initialization could be awaited during route registration.

### Minor

7. **Inconsistent style**: The `update_available` WS event does not have a `missionId` field, but the WebSocket subscription filter in `events.ts:104` skips events that have a `missionId` if the client hasn't subscribed to that mission. This is actually fine — the event won't have `missionId` so it'll be broadcast to all clients. No action needed.

## Fixes to Apply

### Fix 1: Remove `.kilo/plans/` from PR
- Delete the file from the branch: `git rm .kilo/plans/1781217897555-.md`

### Fix 2: Remove unused `access` import in `packages/backend/src/routes/update.ts`
- Change `import { writeFile, access } from "fs/promises";` to `import { writeFile } from "fs/promises";`

### Fix 3: Add flock to `scripts/cron-update.sh`
- Add `flock -n` with a lock file to prevent concurrent runs:
  ```bash
  exec 200>"$PROJECT_DIR/.update.lock"
  flock -n 200 || { echo "$LOG_PREFIX Another update is running"; exit 0; }
  ```

### Fix 4: Add `/health` to vite dev proxy in `packages/frontend/vite.config.ts`
- Add to the proxy config:
  ```ts
  "/health": "http://localhost:3000",
  ```

### Fix 5: Fix `behindBy` fallback in `packages/backend/src/routes/update.ts`
- Change the catch fallback from `1` to `0` — the `updateAvailable = true` is sufficient to trigger the UI notification without a misleading count.
