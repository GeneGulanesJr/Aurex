# Plan: E2E Testing Against Real Services

## Goal
Create vitest integration tests that spin up real service instances in-process — a real LaPis HTTP server backed by an in-memory SQLite database, a real PiNyx stub, and real git operations in temp directories — then exercise the Aurex backend's HTTP clients, Fastify routes, and worktree manager against them. No mocks.

## Design Decisions
- **In-process services**: LaPis HTTP server runs on an ephemeral port via `createDb({ db_path: ':memory:' })` + `createHttpServer()` + `createAurexRepository()`. PiNyx stub uses the existing `scripts/pinyx-stub.mjs` pattern inlined in Node.
- **PiNyx stub only**: The real PiNyx requires Rust. A stub responds to `/health` and `/v1/models` — sufficient for backend startup healthchecks and `PinyxClient.ping()`. The chat endpoint returns a fixed planning response.
- **Pi SDK remains mocked**: One optional smoke test if the SDK is available. All other tests keep the Pi SDK mock — it's too expensive/flaky for CI.
- **Vitest `integration` pool**: Tests run sequentially in a dedicated vitest pool to avoid port/DB collisions. A global setup file starts the LaPis + PiNyx servers once, a teardown shuts them down.

## Architecture

```
__tests__/integration/
├── helpers/
│   ├── lapis-server.ts     — spins up in-process LaPis HTTP server (in-memory SQLite)
│   ├── pinyx-stub.ts       — spins up in-process PiNyx stub server
│   └── git-fixture.ts      — creates temp git repo for worktree tests
├── lapis-client.integration.test.ts   — real HTTP to LaPis
├── pinyx-client.integration.test.ts   — real HTTP to PiNyx stub
├── checkpoint-manager.integration.test.ts — real create/poll/resolve cycle
├── server.integration.test.ts         — full Fastify server backed by real services
├── worktree.integration.test.ts       — real git operations in temp dir
└── pi-sdk-smoke.integration.test.ts   — optional, skipped if SDK unavailable
```

## Step 2: Create test helper — `helpers/lapis-server.ts`

**New file**: `packages/backend/__tests__/integration/helpers/lapis-server.ts`

Uses LaPis's own test infrastructure pattern (from their `test/http-server.test.js`):
1. Calls `createDb({ db_path: ':memory:' })` to get an in-memory SQLite with migrations applied
2. Creates `aurex = createAurexRepository({ sqlJson, sqlRun })`  
3. Creates `server = createHttpServer({ repositories: { aurex }, sqlJson, sqlRun })`
4. Binds to `127.0.0.1:0` (OS-assigned ephemeral port)
5. Exposes `url` (e.g. `http://127.0.0.1:54321`), `server`, and `aurex` repository
6. Provides `close()` method

## Step 8: Integration test — Full Fastify server

**New file**: `packages/backend/__tests__/integration/server.integration.test.ts`

Starts the real Aurex Fastify server backed by real services:
1. LaPis server + PiNyx stub via helpers
2. Creates full `Fastify()` instance with real routes, auth, websocket
3. Starts on ephemeral port
4. Tests:

## Execution Order

1. Add `@genegulanesjr/lapis` dev dependency and install
2. Create helper files (steps 2-4) — no dependencies between them
3. Create integration tests (steps 5-10) — each depends on relevant helpers
4. Add vitest config and script (step 11)
5. Run `pnpm test:integration` and verify all pass
6. Run `pnpm test` to verify existing unit tests still pass

## Risk: LaPis CommonJS Import

LaPis is CommonJS (`"type": "commonjs"`) while Aurex backend is ESM (`"type": "module"`). The helpers will need to use `createRequire()` or dynamic `import()` to load LaPis modules. If this proves problematic, an alternative is to spawn LaPis as a child process (`node cli.js serve --port 0`) and parse the port from stdout, though this is slower and less clean than in-process.
