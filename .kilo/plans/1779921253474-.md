# Aurex — What's NOT Yet Implemented

Analysis of three plan documents vs current codebase (30 commits, ~109 files, ~8,710 lines).

---

## Confirmed Gaps

### 1. Research Agent Spawning in Milestone Loop
- **Plan ref**: Restructuring plan Task 15, Worker spawning plan Task 8, Design doc §3c (research agents spawned during milestone execution)
- **Status**: `research-tools.ts` exists with `write_finding` + `search_memory` tools. `agent-spawner.ts` supports research agent type. BUT `milestone-loop.ts` has **zero references** to research agents — it only spawns workers and validators.
- **Gap**: The milestone loop never triggers research agent sessions during execution. Research findings are never gathered or written.

### 2. WebSocket Event Replay on Reconnect
- **Plan ref**: Overall build plan Issue 7.3, Open Question #4
- **Status**: `ws/events.ts` has a pub/sub EventBus. No event persistence or replay mechanism. Disconnected clients lose all events that occurred during disconnection.
- **Gap**: No event store, no replay API, no sequence numbers on events.

### 3. Authentication
- **Plan ref**: Overall build plan Open Question #5, Design doc §8b
- **Status**: No auth between frontend and backend. All endpoints are open. The design says "localhost/Docker network only."
- **Gap**: No API key, JWT, session, or any auth mechanism. Suitable only for local/trusted network use.

### 4. Multi-Mission Support
- **Plan ref**: Overall build plan Open Question #3, Orchestrator runtime design §1 ("Single mission at a time")
- **Status**: `mission-runner.ts` explicitly rejects new missions when one is active: `throw new Error('Runner already running...')`.
- **Gap**: Only one mission can execute at a time. A mission queue or concurrent runners don't exist.

### 5. Docker Compose E2E Integration Test
- **Plan ref**: Overall build plan Issue 9.3
- **Status**: `docker-compose.yml` exists, both Dockerfiles exist, `nginx.conf` exists. No automated test validates the full stack.
- **Gap**: No test script that starts containers, creates a mission through the frontend, and verifies end-to-end flow.

### 6. PiMemoryExtension Checkpoint Endpoints
- **Plan ref**: Orchestrator runtime plan Tasks 3-4
- **Status**: `lapis-client.ts` calls `POST /checkpoints`, `GET /checkpoints/:id`, `PATCH /checkpoints/:id`, `GET /missions/:missionId/checkpoints`, `GET /missions`. These are HTTP calls to LaPis/PiMemoryExtension.
- **Gap**: The PiMemoryExtension (separate repo) needs migration V12 (checkpoints table), checkpoint repository methods, checkpoint HTTP handlers, and mission listing routes. If not deployed, checkpoint creation/polling/resolution will fail at runtime.

### 7. End-to-End Testing Against Real Services
- **Plan ref**: N/A (all 38 test files use mocks)
- **Status**: All 4,514 lines of tests use `vi.fn()` mocks for LaPis client, PiNyx client, and Pi SDK. No test runs against real LaPis HTTP server or real PiNyx gateway.
- **Gap**: No integration test validating actual HTTP communication, real git worktree creation, or real Pi SDK session lifecycle.

## Summary

The codebase is ~95% implemented against the three plan documents. The main functional gaps are:

1. **Research agents in the loop** (design feature, not built)
2. **WS event replay** (explicitly deferred)
3. **Auth** (explicitly deferred)
4. **Multi-mission** (intentional single-mission design, future enhancement)
5. **PiMemoryExtension deployment** (external dependency)
6. **E2E integration tests** (no real-service validation)

Everything else — types, config, clients, enforcement, agent spawning, milestone loop, validators, negotiator, planner, checkpoints, mission runner, server wiring, frontend dashboard, animations, Docker — is implemented with comprehensive test coverage.
