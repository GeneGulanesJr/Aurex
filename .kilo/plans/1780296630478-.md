# Dummy Implementation Review — Aurex Mission Control

## Methodology

Read every source file in `packages/backend/src/`, `packages/frontend/src/`, `packages/shared/src/`, and `scripts/`. Searched for TODO/FIXME/stub/dummy/placeholder markers, empty bodies, hardcoded returns, no-op functions, and logic that appears to be a shell rather than a real implementation.

---

## Finding 1: `validationContractId` always empty string, `description` duplicates `title`

**File:** `packages/backend/src/orchestrator/mission-runner.ts:118-126`

```ts
const plannedMilestones: Milestone[] = planResult.milestones.map((milestone, index) => ({
  id: milestone.id,
  missionId,
  title: milestone.title,
  description: milestone.title,          // <-- duplicates title, loses planner description
  orderIndex: index,
  status: "planned",
  validationContractId: "",              // <-- always empty
}));
```

The planner (`planner.ts`) generates milestones with both `title` and `description` and stores them in LaPis, but when the mission runner constructs the in-memory `Milestone[]` array to feed into the milestone loop, it throws away the description and uses the title instead. It also hardcodes `validationContractId` to an empty string, even though the planner creates contracts and the milestone loop references contract data from the contract history. These are real data fields that should be populated from what the planner stored.

**Impact:** The milestone description passed to agents and the UI is the title, not the richer description the planner produced. The contract ID reference is never set on the milestone record, though the code works around this by fetching contracts directly.

## Finding 5: `sessionId` is empty string for worker snapshots

**File:** `packages/backend/src/orchestrator/milestone-loop.ts:149`

```ts
callbacks.onAgentStatus(agentId, "worker", "spawned", milestone.id, {
  declaredPaths: unit.declaredPaths,
  declaredModules: unit.declaredModules,
  taskBranch,
  worktreePath,
  sessionId: "",                        // <-- always empty at this point
  description: unit.description,
});
```

The `sessionId` is emitted as an empty string in the initial "spawned" status callback because the agent session hasn't been created yet. The session ID is only available later when `createAgentSession` completes. The later "working" status callback at line 165 doesn't include a `workerSnapshot` at all, so the empty sessionId is the only one the frontend ever sees for this worker.

**Impact:** Low — the frontend doesn't currently use sessionId for anything visible, but the data is misleading.

## Finding 6: `createSpin` falls back to a no-op animation when `.status-dot` is missing

**File:** `packages/frontend/src/animations/agent-animations.ts:14-21`

```ts
export function createSpin(element: HTMLElement) {
  const dot = element.querySelector(".status-dot");
  if (!dot) {
    return animate(element, {
      opacity: [1, 1],                   // <-- no-op: animates opacity from 1 to 1
      duration: 0,
    });
  }
```

If the element doesn't contain a `.status-dot` child, the spin animation silently becomes a no-op (opacity 1→1, duration 0). This means if the DOM structure changes and the `.status-dot` class is missing, the animation won't show anything but won't error either. In `MissionPipeline.tsx:257`, `createSpin` is called on the `WorkerChip` wrapper `div`, which does contain a `.status-dot` child, so this path isn't currently hit. But the fallback is still a dummy implementation.

**Impact:** Low — defensive fallback that currently works correctly.

## Finding 9: `staggerEntrance` animation is never called from any component

**File:** `packages/frontend/src/animations/stagger.ts:3-11`

```ts
export function staggerEntrance(elements: HTMLElement[]) {
  return animate(elements, {
    opacity: [0, 1],
    translateY: [20, 0],
    delay: stagger(100),
    duration: 400,
    ease: "outExpo",
  });
}
```

The DESIGN.md specifies this should be used for "AgentGrid" when "agents appear (mission start, new agent spawned)", but no component imports or calls `staggerEntrance`. The worker chips in `MissionPipeline.tsx` use individual `createPulse`/`createSpin`/`createIdle` instead.

**Impact:** Medium — the staggered entrance animation for agent grids is defined but unused, contradicting the design spec.

## Finding 10: `animateCounter` and `animateProgress` are never called

**File:** `packages/frontend/src/animations/counters.ts`

Both `animateCounter` (for cost counters, telemetry values) and `animateProgress` (for milestone bar) are defined per the DESIGN.md spec but are never imported or called from any component. The `TelemetryBar` and `MissionPipeline` display values directly without animation.

**Impact:** Medium — the counter/progress animation functions exist but are completely unwired.

## Recommended Fixes (Priority Order)

1. **Finding 1** — In `mission-runner.ts`, fetch the stored milestone data (including `description` and `validationContractId`) from LaPis after the planner creates them, rather than reconstructing milestones from the plan result with missing fields.
2. **Findings 9, 10** — Wire `staggerEntrance`, `animateCounter`, and `animateProgress` into their target components as specified in DESIGN.md.
3. **Finding 4** — Pass `onExampleClick` through from `StatusBoard` → `App` → `EmptyState` to make example cards functional.
4. **Finding 7** — Add a total cost footer to the mission sidebar when missions exist, pulling from the selected mission's cost data.
5. **Finding 8** — Pass `memory` usage data to `TelemetryBar` (if available from the backend) or remove the dead code.
