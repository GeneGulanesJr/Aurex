# Frontend Audit — "Looks Implemented, Actually Broken"

Audit of `packages/frontend/src` (React 19 + Vite + Auth0 + WS). Findings verified against source.
Priority: **HIGH** = silent failure / data loss / stuck UI; **MEDIUM** = degraded UX or latent bug; **LOW** = cosmetic / fragile.

Overall: the data/hooks layer (`api.ts`, `useMission(s)`, `useWebSocket`, `useSettings`, `useQuota`, `useSupplyChain`) is genuinely robust — persistence, loading/error/empty states, cleanup and reconnect are handled. The defects cluster in the **component layer**: unreachable error UX, ref-driven (non-reactive) data, conditionally-rendered tab forms that lose state, and a few missing effect cleanups.

## 1. STATE THAT DIES ON REFRESH (or on remount)

### 1.1 [HIGH] Repo analysis errors are swallowed → the `ANALYSIS FAILED` screen is dead code
- **Files:** `passive/RepoOverviewPanel.tsx:17,66-79` (declares+renders `error`); callers `active/MissionCreationView.tsx:396-407` and `passive/StatusBoard.tsx:113-120` (never pass `error`); data source `App.tsx:254-286`.
- **Looks like:** A polished "ANALYSIS FAILED" error screen that should appear when repo readiness/hotspots/scan can't load.
- **Actually broken:** `error` is declared optional and rendered, but **no caller ever passes it**, and the `preparedRepo` shape (`StatusBoard.tsx:35-45`, `App.tsx:61-71`) has no `error` field. Worse, in `App.tsx:260-285` every sub-fetch is `.catch(() => null)` and the outer `catch` (283-285) only flips `loading:false`. So on any analysis failure the user sees an endless stack of "No readiness data / No package scan findings / No hotspot data / No module data" with no indication anything errored — exactly what the error UI was meant to prevent.
- **Fix:** Thread a real `error` string through `preparedRepo` (set it in the `catch` blocks instead of swallowing), add it to the `preparedRepo` type, forward from `StatusBoard`/`MissionCreationView`, and lower the `error && allEmpty` gate at line 68 so partial failures also surface a banner.

### 1.2 [MEDIUM] Inspector error banner never auto-expands for late-arriving errors
- **File:** `passive/StatusBoard.tsx:69-70`
- **Looks like:** The non-recoverable error banner pops open ("DETAILS" expanded) when errors exist.
- **Actually broken:** `errorBannerExpanded` is initialized once via `useState(() => nonRecoverableErrors.length > 0)`. If the first render had no errors, it's locked to `false`; when an error arrives later the banner renders (133) but stays collapsed, so the user only sees the single latest error line (201-203) and must manually click DETAILS.
- **Fix:** Sync with an effect: `useEffect(() => { if (nonRecoverableErrors.length) setErrorBannerExpanded(true); }, [nonRecoverableErrors.length]);`

### 1.3 [MEDIUM] PiNyx tab forms lose all state on tab switch (unsaved edits silently discarded)
- **Files:** `active/IntegrationsPanel.tsx:140-148` (conditional render of each tab) + `active/PinyxConnectionTab.tsx:18-22`, `active/PinyxKeysTab.tsx:26-31`, `active/PinyxModelsTab.tsx:20-31,39-46`.
- **Looks like:** Edit a provider key / set per-agent model routing in a tabbed form.
- **Actually broken:** Each tab is conditionally mounted (`pinyxTab === "connection" && …`), so switching tabs **unmounts** the component and wipes `testResult`, `draft`, `editingIndex`, `modelHints`, `defaultModel`, `overrides`, etc. Returning to the tab shows a fresh state. Manually-chosen per-agent model overrides (`PinyxModelsTab.tsx:98-108`) vanish with no warning; only explicit Save persists.
- **Fix:** Keep all three tabs mounted and toggle visibility via CSS, or lift draft/dirty state into `IntegrationsPanel` and add an unsaved-changes guard before switching.

### 1.4 [LOW] Supply-chain panel / worker-chip collapse state resets on refresh
- **Files:** `passive/SupplyChainPanel.tsx:23` (`collapsed`); `passive/MissionPipeline.tsx:328` (`expanded` in `WorkerChip`).
- **Looks like:** Collapsible sections that remember open/closed during a session.
- **Actually broken:** Bare `useState`, never persisted. A refresh re-expands the supply-chain panel and re-collapses every worker chip mid-investigation.
- **Fix:** Persist to `sessionStorage` keyed by mission id (the app already does this for the mission draft and integrations return state).

## 2. FEATURES WIRED TO NOTHING (or partially)

### 2.1 [HIGH] RepoPrepareModal is un-cancellable during a hanging clone
- **File:** `active/RepoPrepareModal.tsx:40,149-151`
- **Looks like:** A multi-phase prepare modal with a Cancel button + backdrop-click dismiss.
- **Actually broken:** During `cloning`/`indexing`, Cancel is `disabled={isWorking}` (149) **and** backdrop click is `onClick={isWorking ? undefined : onCancel}` (40). If the clone hangs server-side, the full-screen (`position:fixed; z-index:120`) modal has no dismiss/abort path — the user is trapped. There is no client-side timeout. (Also line 150: `{phase === "complete" ? "Cancel" : "Cancel"}` is a dead ternary.)
- **Fix:** Add a force-cancel/abort that closes the modal (and ideally aborts the prepare) while working, or a timeout that flips to the error phase.

### 2.2 [MEDIUM] RepoPrepareModal shows "REPOSITORY READY ✓" even when indexing failed
- **File:** `active/RepoPrepareModal.ts:66,124-138`; parent `active/MissionCreationView.tsx:157-166`.
- **Looks like:** A green "Ready" state with file/symbol counts before "Use Repo".
- **Actually broken:** The parent sets `phase="complete"` even when `exploreRepo` throws (164-166) and when `summary` is missing. The modal then shows "REPOSITORY READY ✓" (66) with the summary block simply hidden (124), so the user sees "READY" + a working "Use Repo" button while indexing actually failed. The server's own `indexed`/`indexingStatus` from `prepareGitHubRepo` is ignored.
- **Fix:** Don't transition to `complete` on explore failure (use an `indexing_failed` phase); honor `prepared.indexed`/`indexingStatus`.

### 2.3 [MEDIUM] DecisionActions guidance textarea leaks across escalation events
- **File:** `active/DecisionActions.tsx:20-21,34-35,43-44` (consumed by `EscalationOverlay.tsx:48`).
- **Looks like:** An "Add Guidance" textarea that annotates a decision.
- **Actually broken:** `guidance`/`showGuidance` are component state with no reset when `trigger` changes. If two escalations arrive back-to-back (the overlay stays mounted because `state.escalation` never passes through `null`), the previously typed guidance is reused for the unrelated checkpoint — stale guidance silently submitted. (cost_cap/quota milestones also never offer guidance at all.)
- **Fix:** Reset `guidance`/`showGuidance` via a `useEffect` keyed on trigger identity/checkpoint id, or key the component by checkpoint id.

### 2.4 [LOW] Collapsed sidebar "+" lets you start a mission when system isn't ready
- **File:** `active/MissionSidebar.tsx:39-59` (collapsed) vs `:95` (expanded).
- **Looks like:** A "+" new-mission affordance in rail and expanded sidebar.
- **Actually broken:** Expanded "+" is gated `{systemReady && (...)}`; the collapsed rail "+" has no `systemReady` check and calls `handleNewMission` unconditionally.
- **Fix:** Gate the collapsed "+" on `systemReady` too.

### 2.5 [LOW] New-mission triggered via a hidden global `window` CustomEvent
- **File:** `active/MissionSidebar.tsx:19-24` (dispatch) → `active/MissionCreationView.tsx:109-121` (listener).
- **Looks like:** Clicking "+" focuses the creation box.
- **Actually broken:** The coupling is invisible at the type level (not in `MissionSidebarProps`). If `MissionCreationView` isn't mounted/listening, the focus silently does nothing — no feedback.
- **Fix:** Pass an explicit `onNewMission` callback prop through the tree.

## 3. OPTIMISTIC UI WITH NO REAL SYNC

### 3.1 [HIGH] MutationPanel loses in-flight runs on remount → duplicate concurrent runs
- **File:** `active/MutationPanel.tsx:33` (`runStatus` init `{state:"idle"}`), `51-77`.
- **Looks like:** A "Run Mutation Tests" button tracking a long-running server job.
- **Actually broken:** `runStatus` is local state with no rehydration. On unmount (start a mission → panel gone; or page refresh) the server keeps running but the client forgets it. On remount the button shows "Run Mutation Tests" again, so the user can start a **second concurrent run** for the same repo. No lookup of an in-flight run exists.
- **Fix:** On mount, query the backend for an active run for `repoName` (or have `getMutationSummary` return an in-flight `runId`) and resume polling.

### 3.2 [HIGH] MutationPanel polling interval never cleared when `repoName` changes → leak + cross-repo polling
- **File:** `active/MutationPanel.tsx:45-49` (cleanup effect, empty deps) + `51-77`.
- **Looks like:** Live progress for the selected repo's mutation run.
- **Actually broken:** `startRun` (dep `[repoName]`) sets `pollRef.current = setInterval(...)`, but the only cleanup is the unmount effect (empty deps). When the user switches repos while a run is in progress, the old interval keeps polling `getMutationRunStatus(<oldRepo>, <oldRunId>)` via its closure, and starting a new run overwrites `pollRef.current` so the old interval can never be cleared. Result: leaked interval, two polls running, and `runStatus`/`summary` visual desync.
- **Fix:** Clear the interval when `repoName` changes (`useEffect(() => () => clearInterval(pollRef.current), [repoName])`) and before starting a new run.

### 3.3 [MEDIUM] PiNyx connection "green dot" shows healthy without any connectivity check
- **File:** `active/PinyxConnectionTab.tsx:76-80`.
- **Looks like:** A green success dot + "Managed by Docker — <endpoint>" reads as "PiNyx is connected".
- **Actually broken:** The dot is `--success` whenever `config.endpoint.trim()` is truthy — purely because an endpoint string exists. No health check has run; an unreachable/misconfigured gateway still shows green. Connectivity is only verified on explicit "Check Gateway" (86).
- **Fix:** Drive the dot from the actual status result (unknown/grey until tested, green on success, red on failure).

### 3.4 [LOW] PinyxKeysTab save path computes the provider list twice with divergent shapes
- **File:** `active/PinyxKeysTab.tsx:97-179`.
- **Looks like:** A normal "save provider / set key" form.
- **Actually broken:** The built-in provider handling is built twice: first preserving `hasApiKey` (104-122), then overwritten in the `editingBuiltIn` branch (138-149) **without** `hasApiKey`. It only avoids stripping the key because the Save button is disabled when `isEditingBuiltIn && !draft.apiKey` (301) — correctness depends entirely on a UI disabled-state. A future refactor/test reaching that branch without a fresh key would silently drop the "has key" marker.
- **Fix:** Compute the next provider list once, immutably; derive `hasApiKey` from whether a key was provided.

## 4. MISSING LOADING / ERROR / EMPTY STATES

### 4.1 [MEDIUM] RepoPicker can't distinguish "loading" from "no repos"
- **File:** `active/RepoPicker.tsx:10-14,44-55`.
- **Looks like:** A searchable repo list with a "No repos found" empty state.
- **Actually broken:** No `loading` concept; empty `repos` always renders "No repos found". (Currently masked because the parent only renders `RepoPicker` when `repos.length>0`, `MissionCreationView.tsx:245`, and shows its own loading row at 248-262 — so the empty state is effectively unreachable today. Relaxing that guard would show "No repos found" while still loading.)
- **Fix:** Accept an optional `loading` prop; show "Loading repos…" vs "No repos found" distinctly.

### 4.2 [MEDIUM] AttemptHistory renders nothing (silent empty) when its optional data is absent
- **Files:** `active/AttemptHistory.tsx:7-8` (returns `null` when empty); consumed `active/CheckpointPanel.tsx:23`.
- **Looks like:** On a "Rescope Limit Reached" escalation, the user expects the prior-attempts list to decide whether to continue/rescope/abort.
- **Actually broken:** `trigger.attemptHistory` is optional and present only on the `rescope_limit` kind; the server may omit it. `CheckpointPanel` passes `?? []` → `AttemptHistory` returns `null`. The user sees only the heading with no attempt details and no explanation that details are unavailable.
- **Fix:** Render an explicit placeholder row ("No attempt details available") instead of `null`.

### 4.3 [MEDIUM] CheckpointPanel switch has no default — unknown trigger kinds render nothing
- **File:** `active/CheckpointPanel.tsx:9-63`.
- **Looks like:** Every escalation kind shows a tailored description.
- **Actually broken:** No `default` case. A new/unknown `kind` falls through and returns `undefined`; `EscalationOverlay` then shows decision buttons with **no description of what's happening**. Also `validation_failed` omits the `AttemptHistory` that `rescope_limit` shows, so validation failures give no attempt context.
- **Fix:** Add a `default` rendering a generic "Unknown escalation" panel; consider surfacing `AttemptHistory` for `validation_failed`.

### 4.4 [MEDIUM] RepoPrepareModal error phase has no retry; real server error is discarded
- **Files:** `active/RepoPrepareModal.tsx:152-157` (primary button only for confirm/complete); parent `active/MissionCreationView.tsx:149-152`.
- **Looks like:** A multi-phase modal with a "PREPARATION FAILED" state.
- **Actually broken:** In the error phase the only action is Cancel; there's no in-modal Retry. The parent also hardcodes "Could not clone repository…" and discards the actual server error.
- **Fix:** Add a Retry action that re-runs `prepareGitHubRepo`; surface the real server error message.

### 4.5 [LOW] LoginScreen has no failure state if `loginWithRedirect` rejects
- **File:** `frame/LoginScreen.tsx:4,41-70`.
- **Looks like:** A Google sign-in button with a loading state.
- **Actually broken:** Only `isLoading` is used. `onClick={() => loginWithRedirect()}` is a floating promise with no try/catch and no error surface; on a network blip / OAuth misconfig the button just returns to idle with no message.
- **Fix:** Catch the rejection and render an error line + retry.

### 4.6 [LOW] MutationPanel button label is blank for unexpected run states
- **File:** `active/MutationPanel.tsx:189-193` (all four conditionals).
- **Looks like:** A button that transitions cleanly through states.
- **Actually broken:** Only `idle/starting/running/completed/failed` set a label; any other server `state` (e.g. `"queued"`, `"pending"`) makes all four conditionals false → empty button. `runIsBusy` (79) is also only true for `starting|running`, so such a state would also stop the busy guard.
- **Fix:** Treat anything not `completed`/`failed` as busy; add a fallback label; normalize server state strings.

## 5. NAVIGATION AND ROUTING GAPS

### 5.1 [LOW] TopBar GitHub chip and PiNyx chip both open the same Integrations drawer

- **Looks like:** Two distinct affordances — a GitHub avatar/login chip vs a "PINYX CONNECTED/OFFLINE" status.
- **Actually broken:** Both call `onClick={onOpenIntegrations}`. Clicking the GitHub chip doesn't open anything GitHub-specific; it opens the same generic integrations drawer. Misleadingly distinct visuals, identical behavior.

### 5.2 [LOW] Auth gate only renders LoginScreen on `!isAuthenticated && !authLoading`

No dead routes (the app is a single-view SPA, no router). Note as verified-correct: no dead links.

## 6. PROPS AND DATA THAT NEVER ARRIVE

### 6.1 [MEDIUM] Event stream is ref-driven (non-reactive) → feed can go stale
- **File:** `App.tsx:83` (`eventsRef`), `:121` (mutated in WS handler), `:429` (`events={eventsRef.current}`) → `passive/StatusBoard.tsx:17` → `MissionActivityFeed`, `MissionComplete`, `MissionDebugLog`.
- **Looks like:** A live activity feed / event counts / debug log that update as WS events arrive.
- **Actually broken:** `events` lives in a `useRef` and is mutated in the handler; mutating a ref does **not** schedule a re-render. The feed only updates as a side effect of *other* handlers in `combinedHandler` dispatching state. Any event type that no reducer consumes — e.g. `quota_update`/`update_available` (handled via refs, not state) — is appended to the ref but never displayed until the next state-triggering event. Latent staleness.
- **Fix:** Promote `events` to `useState` (keep the 50-item cap), or bump a `setEventsVersion(v=>v+1)` in the handler.

### 6.2 [MEDIUM] `StatusBoard` non-null-asserts an optional prop → crash risk
- **File:** `passive/StatusBoard.tsx:114`.
- **Looks like:** The mission-creation form's submit handler.
- **Actually broken:** `onSubmit={async (d,u) => { await onExampleClick!(d,u); }}` uses `!` on the optional `onExampleClick?` (declared line 24). If `StatusBoard` is ever rendered without it (tests/storybook/another route), clicking submit throws. Works today only because App always passes it (`App.tsx:436`).
- **Fix:** Guard it (`if (onExampleClick) await onExampleClick(d,u);`) or make the prop required.

### 6.3 [LOW] MissionInspectorPanel "Live Activity" badge caps the real event count at the feed limit
- **File:** `passive/MissionInspectorPanel.tsx:37,44`.
- **Looks like:** A badge showing how many events have happened.
- **Actually broken:** `activityCount = Math.min(eventStreamCount, events.length + logs.length)` then shown as the badge. With 200 events but `eventStreamCount=8`, the badge reads "8" — indistinguishable from a mission with genuinely 8 events. Conflates "shown" with "total".
- **Fix:** Show the real total (`events.length + logs.length`); use `eventStreamCount` only as the feed `limit` (which `MissionActivityFeed.tsx:13` already does correctly).

### 6.4 [LOW] `"kilo/kilo-auto/free"` used as an undocumented "unset" sentinel in 4+ places
- **File:** `active/PinyxModelsTab.tsx:24,62,82,130`.
- **Looks like:** Default/empty model routing.
- **Actually broken:** A literal string stands in for "no value" across init, auto-select gating, the reset effect, and `getCardModel`. If a real model ever has that id, or the backend sentinel changes, routing silently breaks (the value is discarded and replaced with `defaultModel`).
- **Fix:** Centralize `isUnsetModel(value)` (or use `""`/`null`) and document the backend contract.

## 7. EFFECTS AND SUBSCRIPTIONS LEFT OPEN

### 7.1 [MEDIUM] CodeContextPanel double-fetches code context on refresh of an indexed mission
- **File:** `passive/CodeContextPanel.tsx:68-78` (effect, deps `[missionId]`) and `83-95` (effect, deps `[missionId, logBasedIndexingDone]`, with `eslint-disable` at 94).
- **Looks like:** Two effects that fetch summary/graph/hotspots on mount and again once indexing completes, with a guard to avoid re-fetch.
- **Actually broken:** On refresh where the repo was already indexed, rehydrated agent logs can include an `indexingDone` entry. When `logBasedIndexingDone` flips true, Effect 2 re-runs while Effect 1's promises may still be in flight — the guard `if (summary && graph && hotspots) return` is false (still `null`) so it issues **3 more identical fetches**. The `eslint-disable` silences exactly the dependency that would catch this. Result: 6 code-context requests instead of 3 (wasteful, racy).
- **Fix:** Unify into one effect on `[missionId, logBasedIndexingDone]`, or add an explicit `hasFetchedRef` guard; drop the `eslint-disable`.

### 7.2 [MEDIUM] MissionDebugLog copy-status timer is never cleared on unmount
- **File:** `passive/MissionDebugLog.tsx:16,27-32`.
- **Looks like:** A Copy button that flashes "Copied/Failed" and reverts after ~1.4-1.8s.
- **Actually broken:** `copyTimerRef` is set but there's no unmount cleanup. If the inspector unmounts within that window (mission switch, sidebar collapse, abort→terminal), the pending `setTimeout` fires `setCopyState("idle")` on an unmounted component.
- **Fix:** `useEffect(() => () => { if (copyTimerRef.current) clearTimeout(copyTimerRef.current); }, [])`.

### 7.3 [MEDIUM] DependencyGraph schedules an animation inside `onComplete` with no cancellation (animates detached DOM)
- **File:** `passive/DependencyGraph.tsx:59-83` (esp. 68-81).
- **Looks like:** Smooth staggered node+edge entrance animation.
- **Actually broken:** The node animation's `onComplete` queries the captured `svg` ref and starts a *second* `animate` on edges. The effect returns no cleanup. If the component unmounts in the ~500ms+ window between node-anim start and `onComplete`, the ref still points at a detached `<svg>` and anime runs against detached DOM. (Same "animate-and-don't-cancel" pattern recurs in `MissionPipeline.tsx:69-84,100-109`, `MissionActivityFeed.tsx:17-24`, `HotspotHeatmap.tsx:8-18`, `ArchitectureSummary.tsx:9-19`, `MissionComplete.tsx:62-73` — but DependencyGraph is the one that can realistically animate detached nodes.)
- **Fix:** Capture the returned animation handle and return `() => anim.pause()`; in DependencyGraph, also guard `svgRef.current.isConnected` inside `onComplete`.

### 7.4 [MEDIUM] PinyxModelsTab has two effects racing on `config.modelHints`
- **File:** `active/PinyxModelsTab.tsx:50-77` (async fetch+auto-select, deps `[hasKeys, config.modelHints]`) and `79-83` (sync reset, deps `[config.modelHints]`).
- **Looks like:** Models auto-discovered + default auto-selected.
- **Actually broken:** React runs them in order; the sync reset effect overwrites `modelHints`/`defaultModel` from config, then the async fetch's `.then` may overwrite them again on auto-select — a visible flicker and a race where the reset can win while the user is interacting. The auto-select also writes local state that flips `dirty` (48), showing the "Save model routing" nudge (173-177) for changes the user didn't make, with no auto-save.
- **Fix:** Merge the two effects; only auto-select on first load (guard with a ref), not on every config change.

### 7.5 [LOW] MissionPipeline count-based entrance animations mis-slice on shrink
- **File:** `passive/MissionPipeline.tsx:69-84,100-109`.
- **Looks like:** New milestone nodes / worker chips animate in.
- **Actually broken:** Effects depend on `[milestones.length]`/`[workers.length]` and slice "new" nodes via `prevCountRef`. If length ever *decreases* (replan/remove), the ref holds the old larger value, the slice is empty, and subsequent *growth* is also skipped. Brittle "new node" detection.
- **Fix:** Key animation off a monotonic max-seen count with reset on shrink, or animate via per-item `key` changes.

## Verified-solid (checked, no action)
- `api.ts` — complete surface, consistent error throwing; no stub/mock endpoints.
- `useMission` / `useMissions` — loading/error/loadError states, `localStorage` selection persistence, rehydration, cleanup (`cancelled` flags), stale-selection eviction.
- `useWebSocket` — reconnect w/ backoff + max attempts, auth-failure short-circuit, micro-batching, full unmount cleanup, sequence replay.
- `useQuota` — polling + WS subscription + refresh-after-action; `useSupplyChain` — historical load + optimistic scan trigger + error rollback.
- `useSettings`/`useTheme` — `localStorage` persistence + rehydration; `useNewMissionForm` — `sessionStorage` draft persistence.
- `DependencyGraph`/`HotspotHeatmap`/`ArchitectureSummary` — null/empty/error guards before SVG/math.
- `MutationPanel` loading/error/not-configured/empty states and `.catch` on summary fetch.
- Pinyx tabs all genuinely call `savePinyxConfig` and round-trip config through `IntegrationsPanel` + `usePinyxStatus` refresh.
