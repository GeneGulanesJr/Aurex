# Hardware-Aware Code Audit — Aurex Codebase

## Scope

Scanned: `packages/backend/src/` (22 TS files), `packages/frontend/src/` (23 TS/TSX files), `packages/shared/src/` (5 TS files).

**Architecture note**: Entire backend uses factory-function/closure patterns — no classes, no inheritance, no traditional ORM/repository layer. This eliminates Pattern 3 (OOP Overhead) entirely. All findings are limited to Patterns 1, 2, and 4.

---

## Findings

### Finding 1 — EventBus emit() triggers O(n) array shift on every call

```
Location: packages/backend/src/ws/events.ts, emit(), lines 27-37
Pattern:  Pattern 1 — Hot Loop Detection
Evidence: history.splice(0, history.length - MAX_EVENT_HISTORY) executes on every
          emit() call once the 10,000-entry ring buffer is full. splice(0, 1) on a
          10,001-element array shifts 10,000 elements in memory — O(n) per emit.
          Events are emitted for every agent_status, milestone_progress, cost_update,
          escalation, mission_started/completed — potentially hundreds of emits per
          mission lifecycle. Over a long mission: hundreds of O(10,000) shifts.
Severity: Watch
Reason:   Once the 10,000-event history is full, every subsequent emit() performs an
          O(10,000) array splice, making emit amortized O(n) instead of O(1).
```

### Finding 2 — EventBus getEventsSince() performs linear scan over 10,000 entries

```
Location: packages/backend/src/ws/events.ts, getEventsSince(), lines 44-48
Pattern:  Pattern 4 — Branch-Heavy Inner Loops
Evidence: history.findIndex((e) => e.seq > sinceSeq) scans linearly through up to
          10,000 SequencedEvent entries. Called on every WebSocket reconnection replay
          request. No indexing structure (e.g., binary search on sorted seq field).
          The seq field is monotonically increasing — binary search is trivially
          applicable but absent.
Severity: Watch
Reason:   Linear scan over a sorted 10,000-element array on every replay request;
          the data is inherently ordered but accessed via O(n) scan.
```

### Finding 3 — WebSocket replay sends up to 10,000 messages in a tight loop

```
Location: packages/backend/src/ws/events.ts, replay loop, lines 91-98
Pattern:  Pattern 1 — Hot Loop Detection
Evidence: for (const { seq, event } of missed) iterates up to 10,000 entries,
          calling JSON.stringify() + socket.send() per iteration — 10,000 sequential
          serialize-and-send operations with no batching. A disconnected client that
          misses thousands of events triggers this on reconnect.
Severity: Watch
Reason:   Up to 10,000 sequential JSON.stringify + socket.send calls in a single
          synchronous loop body on reconnection, with no backpressure or batching.
```

### Finding 4 — Overlap detection with minimatch() in nested loops

```
Location: packages/backend/src/orchestrator/overlap.ts, checkPreSpawnOverlap(), lines 28-47
Pattern:  Pattern 4 — Branch-Heavy Inner Loops
Evidence: Outer loop over existingUnits; inner logic uses .some() over newModules
          (with .includes() per module), then .some() over newPaths × .some() over
          unit.declaredPaths — each calling minimatch() twice (bidirectional check).
          3 conditional branches per unit: status filter, module overlap check, path
          overlap check. For 20 units × 10 paths × 10 existing paths = up to 4,000
          minimatch() calls per invocation. minimatch is a non-trivial glob matching
          algorithm (not a simple string comparison).
Severity: Watch
Reason:   Nested loops with expensive minimatch() glob matching per path-pair per unit;
          per-invocation cost grows quadratically with unit × path count.
```

### Finding 5 — Post-commit overlap detection with same minimatch nesting

```
Location: packages/backend/src/orchestrator/overlap.ts, detectOverlap(), lines 69-87
Pattern:  Pattern 4 — Branch-Heavy Inner Loops
Evidence: Outer loop over existingUnits with status filter; inner .some() over filePaths
          × .some() over unit.declaredPaths with minimatch(). 2 conditional branches per
          unit. Same quadratic growth as Finding 4 but with single-directional minimatch
          (half the calls). For 20 units × 20 files × 10 patterns = 4,000 minimatch calls.
Severity: Watch
Reason:   Same quadratic minimatch pattern as checkPreSpawnOverlap; cost scales with
          existingUnits × filePaths × declaredPatterns.
```

### Finding 6 — WorkingUnit: 10-field struct, only 4 fields hot in overlap/batch loops

```
Location: packages/shared/src/types.ts:34-44 (WorkingUnit definition)
          Accessed in: packages/backend/src/orchestrator/overlap.ts:28-47,
          packages/backend/src/orchestrator/milestone-loop.ts:78-104
Pattern:  Pattern 2 — Cache-Hostile Struct Layout
Evidence: WorkingUnit has 10 fields (id, milestoneId, description, declaredPaths,
          declaredModules, status, taskBranch, worktreePath, sessionId). The overlap
          detection and batch grouping algorithms only read 4 fields (id, status,
          declaredPaths, declaredModules). The remaining 6 fields (milestoneId,
          description, taskBranch, worktreePath, sessionId + one more) are cold.
          In V8, each WorkingUnit is a heap object with 9 reference slots (~72 bytes
          of pointers); accessing 4/9 means ~56% of the pointer load is unused.
Severity: Low
Reason:   10-field struct with only 4 fields accessed in inner loops, but iteration
          count per milestone is low (typically < 50 working units).
```

## Explicit Non-Findings (patterns present but excluded per hard rules)

| Location | Pattern Present | Excluded Because |
|---|---|---|
| `milestone-loop.ts:86-104` batch grouping | O(n²) with splice | Iteration count < 50 working units per milestone |
| `planner.ts:58-81` nested milestone/unit creation | Sequential HTTP in loop | I/O-bound, not CPU-bound; iteration < 30 |
| `negotiator.ts:22-88` verdict branching | Heavy if/else chain | Iterates over 1-2 verdicts max |
| `handoff-validator.ts:26-31` field validation loop | Loop with conditionals | Fixed 10 iterations, no scaling |
| `mission-runner-pool.ts:57` queue drain | While loop | Iteration count bounded by maxConcurrent (config) |
| `App.tsx:19` event buffer copy | Array spread per event | 50-element cap, frontend non-hot-path |
| All class hierarchies / OOP overhead | Pattern 3 | No classes exist anywhere in codebase |
