# Codebase Review: Connection & Correctness Audit

## Summary

The Aurex monorepo (`shared`, `backend`, `frontend`) is well-structured overall. The component tree, REST routes, WebSocket event bus, and module boundaries are properly wired. All `@aurex/shared` imports resolve correctly across all three packages. The main issues found are in type-safety gaps (hidden by `as any` casts), a missing runtime dependency, and a frontend dev proxy misconfiguration.

---

## Issues Found (by severity)

### HIGH — Bugs / Runtime Failures

#### 1. `minimatch` missing from `packages/backend/package.json` dependencies
- **File:** `packages/backend/src/orchestrator/overlap.ts:3`
- **Detail:** `import { minimatch } from "minimatch"` — used at lines 30 and 120. `minimatch` is only in the root `package.json` devDependencies. It works via hoisting in dev but will fail in production or if pnpm strict mode is enabled.
- **Fix:** Add `"minimatch": "^10.2.5"` to `packages/backend/package.json` dependencies.

#### 2. Hardcoded `finalState: "completed"` in mission runner pool
- **File:** `packages/backend/src/orchestrator/mission-runner-pool.ts:52`
- **Detail:** `eventBus.emit({ type: "mission_completed", missionId, finalState: "completed" } as any)` — always emits `"completed"` even when the mission actually failed or was aborted. The real state is correctly retrieved on line 48 (`entry.runner.getStatus().state`) but then ignored.
- **Fix:** Use the actual state: `finalState: entry.state` (which was set from the runner status on line 48-49).

#### 3. Vite dev proxy WebSocket port mismatch
- **File:** `packages/frontend/vite.config.ts:10`
- **Detail:** WebSocket proxy targets `ws://localhost:3001`, but the backend runs on a single port (default 3000 per `config.ts:100`). The REST proxy correctly points to `http://localhost:3000` (line 8), but the WS proxy won't connect.
- **Fix:** Change `"ws://localhost:3001"` to `"ws://localhost:3000"`.

### MEDIUM — Type Safety / Data Integrity

#### 4. Escalation events emitted with wrong shape (hidden by `as any`)
- **File:** `packages/backend/src/orchestrator/mission-runner.ts:116-121`
- **Detail:** The escalation event is emitted with:
  ```ts
  trigger: { kind: loopResult.trigger, milestoneId: loopResult.milestoneId },
  context: { summary: loopResult.summary, checkpointId },
  ```
  But `WsClientEvent` defines:
  - `trigger: EscalationTrigger` — requires `releaseBranch` (for `milestone_complete`), `attemptHistory` (for `rescope_limit`), or `error`/`lastAttempt` (for `unclassifiable_error`)
  - `context: EscalationContext` — requires `trigger` (string literal), `milestoneId`, `summary` — not `checkpointId`
  
  The `as any` cast hides this mismatch. Frontend `CheckpointPanel` only reads `trigger.kind`, so it partially works, but `AttemptHistory` cannot render `attemptHistory` because it's never sent.
- **Fix:** Either populate the full `EscalationTrigger`/`EscalationContext` shapes, or adjust the shared types to match what's actually emitted.

#### 5. Pool emits events with `as any` bypassing type checking
- **File:** `packages/backend/src/orchestrator/mission-runner-pool.ts:52,74,96`
- **Detail:** All three `eventBus.emit()` calls use `as any` — `mission_completed`, `mission_started`, `mission_queued`. These correspond to `WsClientEvent` union variants defined in `events.ts`, so they should type-check natively. The `as any` casts suggest the types may have been added after the pool code.
- **Fix:** Remove `as any` and ensure the emitted objects match `WsClientEvent` types.

#### 6. Frontend ignores shared REST types
- **File:** `packages/frontend/src/api.ts:22,66`
- **Detail:** `createMission` returns `Promise<{ missionId: string; status: string }>` instead of `CreateMissionResponse` (which types `status` as `MissionStatus`). `getHealth` returns `Promise<{ status: string; ... }>` instead of `HealthResponse` (which types `status` as `"ok" | "degraded"`). `CurrentMissionPayload` duplicates `GetMissionResponse`.
- **Fix:** Import and use types from `@aurex/shared/rest.ts`.

#### 7. No WebSocket reconnection in frontend
- **File:** `packages/frontend/src/hooks/useWebSocket.ts:10-25`
- **Detail:** If the WebSocket connection drops, `connected` becomes `false` and the app permanently shows "Connecting..." with no recovery. No reconnection logic exists.
- **Fix:** Add exponential backoff reconnection on `ws.onclose`.

#### 8. Frontend does not send WebSocket auth
- **File:** `packages/frontend/src/hooks/useWebSocket.ts`, `packages/backend/src/ws/events.ts:84-113`
- **Detail:** Backend requires `{ type: "auth", token: "<apiKey>" }` within 5 seconds if `API_KEY` is set. Frontend never sends this. If auth is enabled, frontend's WebSocket will be closed with code `4001`.
- **Fix:** After `ws.onopen`, send auth message if `apiKey` is configured.

#### 9. `milestone_completed` event emitted twice with different shapes
- **File:** `packages/backend/src/orchestrator/mission-runner-pool.ts:52` AND `packages/backend/src/orchestrator/mission-runner.ts:163-164`
- **Detail:** `mission-runner-pool.ts` emits `mission_completed` when a runner finishes. `mission-runner.ts` also updates the mission status to `"completed"`. The pool's `finalState` is always `"completed"` regardless of actual outcome, and the runner emits the actual outcome via `lapis.updateMissionStatus()`. This could cause confusion in the frontend about the real final state.

### LOW — Minor Issues / Dead Code

#### 10. `agent_status` and `milestone_progress` events ignored by frontend
- **Files:** `packages/frontend/src/hooks/useMission.ts:67-78`, `packages/frontend/src/hooks/useMissions.ts:98-110`
- **Detail:** These event types are emitted by the backend but silently discarded by both hooks. The dashboard cannot update agent statuses or milestone progress in real time — only when the full mission data is refetched.

#### 11. `CostSummary.entries` hardcoded to 0 in frontend
- **File:** `packages/frontend/src/hooks/useMission.ts:33`
- **Detail:** The `COST_UPDATE` action only carries `totalCost` and `totalTokens`, so `entries` is hardcoded to `0`. The actual entry count from LaPis is lost.

#### 12. Frontend `src/types.ts` is dead code
- **File:** `packages/frontend/src/types.ts`
- **Detail:** Re-exports types from `@aurex/shared`, but no file imports from `./types`. Every file imports directly from `@aurex/shared`.

#### 13. Unused animation exports
- **Files:** `src/animations/agent-animations.ts:25-33` (`createScanning`), `src/animations/stagger.ts:13-21` (`staggerExit`)
- **Detail:** These are defined and exported but never imported anywhere.

#### 14. All API errors silently swallowed in frontend hooks
- **Files:** `src/hooks/useMissions.ts:93`, `src/hooks/useMission.ts:62`, `src/active/MissionSidebar.tsx:36`
- **Detail:** `.catch(() => {})` and `catch {}` patterns mean backend errors show as empty states with no user feedback.

#### 15. `StatusFeed` shows render-time instead of event time
- **File:** `packages/frontend/src/passive/StatusFeed.tsx:28`
- **Detail:** `WsClientEvent` types don't carry timestamps, so each event renders with `new Date().toLocaleTimeString()` — the time of render, not the time of the event.

## What Looks Good

- **Shared package** (`@aurex/shared`): Clean type definitions, well-formed discriminated unions, proper barrel exports. All types cross-reference correctly.
- **Server wiring** (`server.ts`): Correctly wires Fastify, WebSocket, auth, health check, routes, event bus, and pool. Startup healthchecks for LaPis + PiNyx. Graceful shutdown with drain.
- **REST routes** (`missions.ts`, `checkpoints.ts`): All 7 routes match between frontend API client and backend. Request/response shapes are compatible.
- **WebSocket event bus** (`events.ts`): Ring buffer with sequence numbers, replay support, auth flow, mission subscription filtering. Well-designed.
- **LaPis client** (`lapis-client.ts`): Comprehensive HTTP client covering all data access patterns. Correctly typed against shared types.
- **PiNyx client** (`pinyx-client.ts`): Clean OpenAI-compatible chat completions wrapper.
- **Agent spawner** (`agent-spawner.ts`): Properly integrates Pi SDK, cost tracking, timeout handling, session registration, and logging.
- **Enforcement modules**: `branch-guard.ts`, `handoff-validator.ts`, `contract-immutability.ts` — all correctly import and validate against shared types.
- **Mission runner** (`mission-runner.ts`): Correct planning → milestone loop → checkpoint → rescope lifecycle. Properly delegates to planner, milestone loop, and checkpoint manager.
- **Frontend component tree**: Well-structured React with clean hooks-based state management. Data flows correctly from `useWebSocket` → `useMissions`/`useMission` → components.
- **Docker/nginx**: Production deployment config is correct — `nginx.conf` proxies both `/api/` and `/ws/` to `backend:3000`.
- **Tests**: 41 test files covering shared types, backend modules, and frontend API client. Comprehensive coverage of enforcement, orchestrator, and route logic.
