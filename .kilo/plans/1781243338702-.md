# PR #95 Review: Add OpenTelemetry metrics and bundled collector

## Summary
The PR adds OTEL observability to the Aurex backend. Overall it's well-structured: clean telemetry module, proper Fastify hooks, good docs, and correct OTLP → Prometheus pipeline. Below are actionable items to address before merging.

## Issues to Fix

### 1. `startTelemetry()` lacks try/catch — server crash on OTEL init failure
**File:** `packages/backend/src/telemetry.ts:67-152`

If `MeterProvider`, `OTLPMetricExporter`, or `PeriodicExportingMetricReader` throws during construction (e.g., malformed env vars, incompatible state), the entire server crashes. Telemetry should degrade gracefully.

**Fix:** Wrap the initialization block in try/catch, returning the disabled handle on failure:
```typescript
export function startTelemetry(): TelemetryHandle {
  if (!isMetricsEnabled()) {
    return { enabled: false, registerFastifyMetrics: () => undefined, shutdown: async () => undefined };
  }
  try {
    // ... existing initialization ...
    return { enabled: true, ... };
  } catch (err) {
    console.warn("[telemetry] Failed to initialize, metrics disabled:", err instanceof Error ? err.message : err);
    return { enabled: false, registerFastifyMetrics: () => undefined, shutdown: async () => undefined };
  }
}
```

### 2. otel-collector missing Docker healthcheck
**File:** `docker-compose.yml`

The collector config declares `health_check` extension on port 13133, but docker-compose uses `service_started` condition. The backend could start exporting before the collector is ready, causing noisy connection-refused errors on first export cycles.

**Fix:** Add healthcheck to the otel-collector service and use `service_healthy`:
```yaml
  otel-collector:
    ...
    healthcheck:
      test: ["CMD", "wget", "--spider", "-q", "http://localhost:13133/"]
      interval: 5s
      timeout: 3s
      retries: 5
```
And change backend's depends_on:
```yaml
      otel-collector: { condition: service_healthy }
```

### 3. Unrelated lockfile noise
**File:** `pnpm-lock.yaml`

The diff removes `libc: [glibc]` / `libc: [musl]` fields from ~20 `@rollup/*` and `@mariozechner/*` package entries. These are unrelated to the OTEL changes — likely caused by a pnpm version difference. Should be reverted or split into a separate commit to keep this PR focused and avoid merge conflicts.

## Minor Observations (non-blocking)

- **`npm_package_version` env var** (`telemetry.ts:91`) — Only set when running through npm/pnpm scripts. When running compiled JS directly, it falls back to `"0.0.0"`. The fallback handles this, but the `"0.1.0"` hardcoded fallback may drift from actual version. Consider reading from `package.json` or a build-time constant instead.
- **OTEL env var standard compliance** — The PR uses `OTEL_METRIC_EXPORT_INTERVAL` and `OTEL_METRIC_EXPORT_TIMEOUT` which are valid OTEL SDK env vars and read explicitly via `envInt()`. This works correctly since the JS SDK `PeriodicExportingMetricReader` does not auto-read these particular vars from env — manual reading is necessary.
- **`service.telemetry.readers` format** in `otel-collector-config.yaml` — Uses the newer v2 collector self-observability config. Compatible with collector v0.129.1.
- **Metric naming** — Uses dot-separated names (e.g., `http.server.requests.total`). While functional, OpenTelemetry semantic conventions prefer underscores for Prometheus compatibility (dots get converted). The collector's Prometheus exporter will sanitize these, so no action needed.
