# Improve Agent Spawner Observability & Robustness

**Decision:** Drop tmux. The current in-process `AgentSpawner` using `createAgentSession()` from `@earendil-works/pi-coding-agent` is the correct architecture — the Pi SDK is designed for in-process use, and the existing spawner already handles lifecycle, timeouts, and event-based completion. Instead, add structured logging and robustness improvements that give the observability tmux would have provided, without the complexity.

---

## What the current spawner already does well

- Session lifecycle: `createAgentSession()` → `session.prompt()` → event subscription → `session.dispose()`
- Timeout supervision: `setTimeout` → `session.abort()` → resolve as `timed_out`
- Cost tracking: event parsing with cumulative cost reporting via `onCost` callback
- Custom tools per agent type: workers get `write_handoff` + `search_memory`, validators get `write_verdict`, research gets `write_finding`
- Crash-safe completion: `Promise.race` between timeout, agent_end, and error events

## What's missing

1. **No structured logging** — when an agent fails, there's no structured log to tell you why. Only `console.error` in mission-runner.
2. **No shutdown tracking** — `shutdown()` is a stub. Active handles aren't tracked, so the server can't gracefully drain agents on shutdown.
3. **No agent output capture** — you can't see what an agent did after the fact. The tmux plan was going to solve this with `capture-pane`; we should solve it with a simple event log.
4. **No concurrent spawn limit** — the milestone loop spawns all non-overlapping workers in a batch with no cap. A burst of 10 workers could exhaust resources.

## Task 1: Agent Event Logger

Add structured logging to the spawner that captures agent lifecycle events in a queryable format.

**Files:**
- Create: `packages/backend/src/agents/agent-logger.ts`
- Create: `packages/backend/__tests__/agents/agent-logger.test.ts`

### Interface

```typescript
export interface AgentLogEntry {
  sessionId: string;
  agentType: AgentType;
  missionId: string;
  milestoneId: string;
  unitId?: string;
  event: "spawned" | "prompt_sent" | "tool_call" | "tool_result" | "cost_update" | "completed" | "timed_out" | "failed" | "aborted";
  timestamp: string;
  data?: Record<string, unknown>;
}

export interface AgentLogger {
  log(entry: Omit<AgentLogEntry, "timestamp">): void;
  getEntries(filter: { missionId?: string; sessionId?: string; event?: string }): AgentLogEntry[];
  getRecent(count: number): AgentLogEntry[];
  clear(sessionId?: string): void;
}
```

### Implementation

- In-memory ring buffer (configurable max size, default 1000 entries per mission)
- `log()` appends with auto-generated ISO timestamp
- `getEntries()` filters by mission/session/event
- Logged from `agent-spawner.ts` event subscription — each Pi SDK event becomes a structured log entry
- Optionally emits entries through the existing `EventBus` so the frontend can display a live agent activity feed

### Tests

- Ring buffer respects max size
- Filter by mission, session, event type
- Clear by session ID

## Task 2: Track Active Handles in Spawner

Make `shutdown()` actually work — track all active `SpawnHandle` instances so the server can abort them on graceful shutdown.

**Files:**
- Modify: `packages/backend/src/agents/agent-spawner.ts`
- Modify: `packages/backend/__tests__/agents/agent-spawner.test.ts`

### Changes

```typescript
export function createAgentSpawner(config: AgentSpawnerConfig) {
  const activeHandles = new Map<string, SpawnHandle>();

  return {
    async spawn(opts: SpawnOptions): Promise<SpawnHandle> {
      // ... existing spawn logic ...
      
      const handle: SpawnHandle = {
        sessionId: session.sessionId,
        completed,
        abort() { /* existing */ },
        dispose() {
          activeHandles.delete(session.sessionId);
          session.dispose();
        },
      };

      activeHandles.set(session.sessionId, handle);
      
      completed.finally(() => {
        activeHandles.delete(session.sessionId);
      });

      return handle;
    },

    shutdown() {
      for (const [id, handle] of activeHandles) {
        handle.abort();
        handle.dispose();
      }
      activeHandles.clear();
    },

    getActiveCount(): number {
      return activeHandles.size;
    },

    getActiveSessions(): string[] {
      return [...activeHandles.keys()];
    },
  };
}
```

### Tests

- `shutdown()` aborts and disposes all active handles
- `getActiveCount()` returns correct count during and after spawning
- Handle auto-removed from tracking on completion

## Task 4: Concurrent Spawn Limit

Add a configurable concurrency cap to the spawner so the milestone loop can't accidentally spawn 20 workers at once.

**Files:**
- Modify: `packages/backend/src/agents/agent-spawner.ts`
- Modify: `packages/backend/__tests__/agents/agent-spawner.test.ts`

### Changes

Add `maxConcurrent` to `AgentSpawnerConfig`:

```typescript
export interface AgentSpawnerConfig {
  // ... existing fields ...
  maxConcurrent?: number; // default: Infinity (no limit)
}
```

When `maxConcurrent` is set and active handles >= limit, `spawn()` throws a clear error:

```typescript
async spawn(opts: SpawnOptions): Promise<SpawnHandle> {
  if (this.maxConcurrent && activeHandles.size >= this.maxConcurrent) {
    throw new Error(
      `AgentSpawner concurrency limit reached (${this.maxConcurrent}). ` +
      `Active sessions: ${[...activeHandles.keys()].join(", ")}`
    );
  }
  // ... existing logic ...
}
```

The milestone loop already handles batches — this is a safety valve, not a scheduler.

### Tests

- Spawn succeeds when under limit
- Spawn throws when at limit
- Spawn succeeds again after a handle completes

Use the improved `shutdown()` to gracefully drain agents when the server receives SIGTERM.

**Files:**
- Modify: `packages/backend/src/server.ts`

### Changes

```typescript
// After pool creation, register shutdown handler
process.on("SIGTERM", async () => {
  console.log("[shutdown] SIGTERM received, draining agents...");
  // Pool stops accepting new missions
  // Existing runners abort their active agents via spawner.shutdown()
  // Wait for in-flight agent sessions to settle (with a hard deadline)
  await Promise.race([
    pool.drain(),
    new Promise((resolve) => setTimeout(resolve, 30_000)),
  ]);
  console.log("[shutdown] Agents drained, exiting");
  process.exit(0);
});
```

Add a `drain()` method to `MissionRunnerPool` that calls `shutdown()` on each runner's spawner.
