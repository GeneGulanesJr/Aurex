# Aurex Frontend Audit — "Looks Implemented, Actually Broken"

Scope: `packages/frontend/src/**` (React + Vite + Tailwind dashboard). Every finding below was verified by reading the actual source (file:line cited). Items confirmed **correctly wired** (e.g. `useSettings` localStorage persistence, `useMissions` selectedMissionId rehydration, `useTheme`, checkpoint WS+REST-fallback reconciliation, `useQuota`/`useBreakpoint`/`useKeyboardShortcuts` cleanup) are **excluded**.

Priority legend: **HIGH** = silent failure / data loss / crash / stuck state / security · **MEDIUM** = degraded UX with real user impact · **LOW** = visual/UX-only.

Quick-jump summary table at the bottom.

## CATEGORY 1 — State that dies on refresh

### 1.1 [MEDIUM] New-mission description textarea is wiped on refresh and on every remount
- **File:** `active/MissionCreationView.tsx:62-64` (mount effect calls `form.open()`), `:294-317` (textarea); reducer `active/useNewMissionForm.ts:23-56`
- **Appears to user:** A large "Describe what you want done…" box where the user composes a (potentially long) mission prompt.
- **Actually broken:** Form state lives in a `useReducer` that is never persisted. On mount, `useEffect(() => { form.open(); }, [])` dispatches `OPEN`, which resets to `initialFormState` (`description: ""`). So (a) a page refresh discards the typed prompt, and (b) selecting another mission and coming back, or clicking "+ New mission", re-runs the reset and silently erases everything typed. Inconsistently, the *repo selection* IS rehydrated via `getSessionState("prepared_repo")` (`MissionCreationView.tsx:71-90`), making the loss of the description more surprising.
- **Fix:** Persist `description` to `sessionState`/`localStorage` and rehydrate it in the reducer initializer; or stop calling `form.open()` unconditionally on mount.

### 1.2 [LOW] Error-banner expand/collapse resets on refresh
- **File:** `passive/StatusBoard.tsx:64` (`errorBannerExpanded` = `useState(false)`), `:83-90`, `:184-196`
- **Appears to user:** A non-recoverable error banner with a "DETAILS" toggle.
- **Actually broken:** Expand state is local `useState`, not persisted. After refresh it re-collapses even if the user had expanded it to read the stack. (Errors themselves are rehydrated; only the toggle resets.)
- **Fix:** Default `errorBannerExpanded` to `true` when `nonRecoverableErrors.length > 0`.

## CATEGORY 2 — Features wired to nothing / stubs / incomplete

### 2.1 [HIGH] Code Context panel never re-fetches after indexing completes on a live mission
- **File:** `passive/CodeContextPanel.tsx:68-81` (fetch effect), `:51,62` (`indexingDone`), `:97-106` (visibility gate)
- **Appears to user:** A "Code Context" section (architecture summary, dependency graph, hotspot heatmap) for the mission's repo that appears once indexing finishes.
- **Actually broken:** The three fetches (`getCodeSummary`/`getCodeGraph`/`getCodeHotspots`) run in a `useEffect` whose only dependency is `[missionId]` (line 81). On a live session the component mounts *before* indexing is done, so all three calls 404 and set `summaryError/graphError/hotspotsError = true` (lines 73/76/79). When a later WS log flips `logBasedIndexingDone → indexingDone = true` (lines 51, 62), the panel becomes *visible* — but the effect **does not re-run** (no dependency on `indexingDone`), so the child panels render with `data=null, error=true` and show "…unavailable" **forever, with no retry**. The misleading code comment at lines 58-67 claims the log path "kicks in," but it only makes the panel visible; it never refetches. The feature works **only** after a manual page refresh.
- **Fix:** Add `indexingDone` (or a derived `shouldFetch`) to the effect deps, or add a separate `useEffect` watching `logBasedIndexingDone` that clears the error flags and re-runs the three fetches once it flips true.

### 2.2 [MEDIUM] Custom PiNyx providers can be added/edited but never deleted
- **File:** `active/PinyxKeysTab.tsx:168-201` (provider table), `:266-278` (edit form actions)
- **Appears to user:** A provider table with "+ Add Custom Provider", an edit (✎) button per row, and Save/Cancel.
- **Actually broken:** There is no delete/remove affordance and no `handleDelete`. You cannot clear a built-in provider's key (Save disabled when `!draft.apiKey.trim()`, line 268) and cannot remove a mistakenly-added custom provider — editing one and blanking its fields is blocked by the same disabled condition. A wrong custom provider is effectively permanent from the UI.
- **Fix:** Add a delete control that filters the provider out before calling `savePinyxConfig`.

### 2.3 [MEDIUM] Saving one PiNyx key may drop `hasApiKey` for the other built-ins (silent key erasure risk)
- **File:** `active/PinyxKeysTab.tsx:81-99`
- **Appears to user:** "Save" one provider's API key; the other already-configured providers keep their "Saved" badge.
- **Actually broken:** For the provider being edited the key status is carefully preserved (lines 89-90), but for every **other** built-in the payload emits `{ id, name, baseUrl, apiKey: existing?.apiKey ?? undefined }` with **no `hasApiKey` field** (lines 93-98). The API client type never returns the secret `apiKey` value (only `hasApiKey`, `api.ts:216-222`), so `existing.apiKey` is `undefined` for all non-edited providers — they are saved with no key reference and no `hasApiKey:true`. Depending on backend semantics this can erase previously-stored keys for providers the user never touched. No rollback on partial failure.
- **Fix:** Preserve `hasApiKey: existing.hasApiKey` for all non-edited providers when rebuilding the list; reload config from the server response to confirm badges.

### 2.4 [LOW] "Continue/Rescope With Guidance" can submit empty guidance
- **File:** `active/DecisionActions.tsx:93-94`
- **Appears to user:** An "Add Guidance" textarea with "Continue With Guidance" / "Rescope With Guidance" buttons.
- **Actually broken:** The top-level buttons fall back to a default when guidance is empty (line 34), but the two expanded buttons call `onDecision(..., { guidance })` / `{ rescopeGuidance: guidance }` with **no fallback and no disabled state**. Clicking them with an empty textarea submits an empty-string guidance — a no-op indistinguishable from the default buttons.
- **Fix:** Apply the same `guidance || <default>` fallback, or disable until guidance is non-empty.

### 2.5 [LOW] Dev-mode auth stubs are inert no-ops (by design)
- **File:** `hooks/useAuth.ts:33-36` (`loginWithRedirect: async () => {}`, `logout: () => {}`)
- **Appears to user:** (dev only, `VITE_AUTH_DISABLED=true`) a sign-in flow exists.
- **Actually broken:** Intentionally stubbed; unreachable because `isAuthenticated` is hard-wired `true` in dev. Not a production bug — flagged only so prod never ships with `VITE_AUTH_DISABLED=true` (already enforced by `main.tsx:14-18`).

## CATEGORY 3 — Optimistic UI with no real sync

### 3.1 [MEDIUM] Supply-chain SCAN has no optimistic scanning state and no rollback
- **File:** `hooks/useSupplyChain.ts:106-113` (`handleTriggerScan`); `passive/SupplyChainPanel.tsx:105-126` (button)
- **Appears to user:** A "SCAN" button that initiates a supply-chain scan and shows "SCANNING…".
- **Actually broken:** `isScanning` is only set `true` by the WS `scan_started` event (`SCAN_STARTED` action), **not** optimistically in `handleTriggerScan`. If the POST succeeds but the `scan_started` WS event is delayed/lost, the button gives no visual feedback. If the POST fails, `SET_ERROR` is dispatched (line 111) but the error is never shown (see 4.4) and there is no rollback because nothing was optimistically applied — the net effect is a click that does nothing visible.
- **Fix:** Set `isScanning=true` optimistically on click (rollback in the catch); surface `state.error` (see 4.4).

> Note: Genuine optimistic-delete/like/reorder features were checked — none found. The checkpoint flow (`useMission.ts:145-176` + `App.tsx:175-242`) is correctly idempotent with WS→REST fallback and rollback-on-reject.

## CATEGORY 4 — Missing loading / error / empty states

### 4.1 [HIGH] Mission detail fetch silently swallows all errors — blank view, no feedback, no retry
- **File:** `hooks/useMission.ts:196-211` (`.catch(() => {})` at line 208); `MissionState` (lines 29-42) has no `loading`/`loadError` field
- **Appears to user:** Selecting a mission loads its detail view (milestones, workers, cost…).
- **Actually broken:** `getMission(missionId)` has an **empty `.catch(() => {})`**. There is no `loading` flag and no load-error surface (the `errors[]` array is populated only by WS `mission_error`, never by a failed REST load). On any fetch failure (500, network drop, auth hiccup), `state.mission` stays `null` forever with **zero feedback and no retry**. The UI cannot distinguish "loading" from "failed" from "empty".
- **Fix:** Add `loading`/`loadError` to `MissionState`; dispatch a load-error in the catch; render a retry affordance in `StatusBoard` when `mission === null && loadError`.

### 4.2 [HIGH] No React error boundary anywhere — any render throw → blank page
- **File:** `main.tsx:22-35` (and absence throughout `App.tsx`)
- **Appears to user:** The dashboard always shows something.
- **Actually broken:** `<App/>` is mounted under `StrictMode` + `Auth0Provider` only. There is **no error boundary**. A single uncaught render error (malformed WS payload dereferenced in a child, an unexpected `null` prop) unmounts the entire tree → blank white page with no recovery UI.
- **Fix:** Wrap `<App/>` (and ideally major sub-trees) in an error boundary with a "Something went wrong — reload" fallback.

### 4.3 [MEDIUM] Agent-log rehydration swallows errors
- **File:** `hooks/useMission.ts:216-243` (`.catch(() => {})` at line 241)
- **Appears to user:** After a refresh, the agent event timeline repopulates.
- **Actually broken:** `getAgentLogs` failure is silently swallowed; the timeline just stays empty with no indication the rehydrate failed (looks like "no events" rather than "failed to load events").
- **Fix:** Surface a non-blocking `logsRehydrateError` flag.

### 4.4 [MEDIUM] Supply-chain SCAN/load errors are tracked in the hook but never displayed
- **File:** `passive/SupplyChainPanel.tsx:4-11` (`SupplyChainPanelProps` has no `error`); `hooks/useSupplyChain.ts:99-101,110-112` (sets `state.error`); consumer `App.tsx:437-440` (passes only `findings, isScanning, scans, onTriggerScan`)
- **Appears to user:** A "SCAN" button + findings list.
- **Actually broken:** `useSupplyChain` tracks `state.error` (set when `listScans` fails on mount and when `triggerScan` fails on click), but `SupplyChainPanel` has **no `error` prop** and `App.tsx` never passes it. So (a) an initial scan-history load failure shows "No scans yet" as if none exist; (b) a clicked SCAN that fails gives **no feedback at all**. The error is computed and then discarded.
- **Fix:** Thread `supplyChainState.error` into `SupplyChainPanel` and render an error row near the SCAN button.

### 4.5 [MEDIUM] DependencyGraph shows a perpetual "LOADING GRAPH…" skeleton for empty graphs (empty-state branch is dead code)
- **File:** `passive/DependencyGraph.tsx:19` (layout memo returns `null` when 0 nodes), `:85-87` (render branches)
- **Appears to user:** A loading skeleton that resolves into a graph; an empty repo should say "no files to graph".
- **Actually broken:** `layout` is `null` whenever `data.nodes.length === 0` (line 19). Render then hits `if (!data || !layout) return <GraphSkeleton />` (line 86) **before** the intended empty-state `if (data.nodes.length === 0) return <Unavailable label="no files to graph" />` (line 87). Because `layout` is already `null` in the empty case, line 87 is unreachable — a graph with zero nodes renders the skeleton forever. (`HotspotHeatmap.tsx` does this correctly.)
- **Fix:** Reorder: `if (error) …; if (!data) return skeleton; if (data.nodes.length === 0) return empty; if (!layout) return skeleton;`

### 4.6 [MEDIUM] Integrations drawer has no loading state for the PiNyx config fetch
- **File:** `active/IntegrationsPanel.tsx:31-34` (fetch), `:127-135` (render gates on `pinyx &&`)
- **Appears to user:** Opening Integrations shows a "Connection / Models / Keys" tab bar for PiNyx.
- **Actually broken:** `getPinyxConfig()` fires on open but there is no `loading` flag. While pending, `pinyx` is `null` and every tab body is gated on `pinyx &&`, so the selected tab renders a **blank body** with no spinner/"Loading…". Only on error does `pinyxError` show. A slow network makes PiNyx look empty/broken.
- **Fix:** Add a `pinyxLoading` state and render a skeleton until it resolves.

### 4.7 [MEDIUM] Quota fetch swallows errors; chip silently shows nothing on failure
- **File:** `hooks/useQuota.ts:25-29` (`.catch(() => { setLoading(false); })`), `:31-35` (same in 30s poll)
- **Appears to user:** The TopBar quota chip and QuotaPanel reflect quota status.
- **Actually broken:** Any failure (initial or poll) just flips `loading` off and leaves `status === null`. No error state, so the chip shows nothing and the panel cannot report the quota backend is unreachable.
- **Fix:** Add an `error` state; show "quota unavailable" on failure.

### 4.8 [MEDIUM] GitHub repo list fails silently to empty
- **File:** `hooks/useGitHub.ts:36-43` (catch sets `repos: []`, no `error`)
- **Appears to user:** After connecting GitHub, the repo picker lists the user's repos.
- **Actually broken:** If `getGitHubRepos()` fails (rate limit, transient error), the list is silently set to `[]` with **no `error`** — so the user sees an empty list and may believe they have no repos. (Contrast `refreshStatus`, which does set an error string.)
- **Fix:** Set a distinct error (e.g. "Failed to load repositories") in the catch.

### 4.9 [LOW] PiNyx status conflates "fetch failed" with "not configured"
- **File:** `hooks/usePinyxStatus.ts:19-26` (catch at 23-25 sets `configured: false`)
- **Appears to user:** TopBar shows "PINYX CONNECTED" / "PINYX OFFLINE".
- **Actually broken:** Any fetch failure is reported as `configured: false`, so a transient network blip shows "PINYX OFFLINE" even when PiNyx is configured. No error vs. not-configured distinction.
- **Fix:** Separate `error` from `configured`; only flip `configured` on a successful response.

### 4.10 [LOW] Update-status fetch swallows errors; update chip simply never appears
- **File:** `hooks/useUpdateStatus.ts:34-36` (`.catch(() => {})` at 35), `:57` (`checkNow` only `console.warn`s)
- **Appears to user:** An "UPDATE" chip appears when a new build is available.
- **Actually broken:** If `getUpdateStatus()` fails, the chip never appears and there is no signal the check failed. Manual `checkNow` only `console.warn`s.
- **Fix:** Track a load error and expose it to the TopBar.

### 4.11 [LOW] RepoOverviewPanel has no error state; fetch failures look like an empty repo
- **File:** `passive/RepoOverviewPanel.tsx:44-63` (only a `loading` guard)
- **Appears to user:** A rich repo map (modules, hotspots, readiness, package scan, suggestions).
- **Actually broken:** Only `loading` vs loaded is distinguished. If the parent's explore/summary/hotspots/readiness/scan fetches **fail**, `loading` becomes false and every nullable prop is `null`, so the user sees a page of "No … data" cards. A server-side failure is indistinguishable from a genuinely empty repo.
- **Fix:** Accept an optional `error?: string` prop and render a "Couldn't analyze this repository — Retry" banner when all data is null and not loading.

### 4.12 [LOW] Quota action buttons have no in-flight disabled/spinner state
- **File:** `active/QuotaPanel.tsx:45-105`
- **Appears to user:** ENABLED/DISABLED, TRACKED/UNTRACKED, Prefire, Reset, Calculate buttons that look instantly clickable.
- **Actually broken:** Each handler `await`s an API call but no button is disabled/spinner while in flight. Toggles read from `status` (pre-mutation value), so during a slow request a user can click again and flip the value back or fire duplicates. Errors are shown and `refresh()` reconciles on success, so this is UX rather than data loss.
- **Fix:** Track a `busy`/`pendingAction` state and disable the relevant button until the call settles.

## CATEGORY 5 — Navigation, routing & auth gaps

### 5.1 [HIGH] WebSocket never logs out a dead session — stuck on "CONNECTING…" forever
- **File:** `hooks/useWebSocket.ts:105-126` (auth failure closes socket → `onclose` → `scheduleReconnect`), `:206-217` (reconnect has no max-retry, no close-code inspection); `App.tsx:350-374` (connecting overlay)
- **Appears to user:** When the session expires, the app shows "CONNECTING…" and appears to be recovering.
- **Actually broken:** When `getToken()` throws (line 109-112) the socket closes with code `4003`, and `onclose` (121-126) **unconditionally** calls `scheduleReconnect()`. That function (206-217) has **no max-retry limit and ignores the close code/reason** — it backs off up to 30s and retries **forever**. Critically, unlike the REST path (`api.ts:29-32` calls `_onAuthError?.()` → `logout()`), the WS auth-failure path **never triggers the auth-error handler / logout**. A user whose session is dead gets a gentle-but-permanent reconnect loop and is never sent back to login; the app sits on the "CONNECTING…" overlay indefinitely.
- **Fix:** Inspect `CloseEvent.code`/`reason` in `onclose`; for auth codes (4003/4001/1008) either stop reconnecting or invoke an `onAuthError` callback (mirror `api.ts`). Cap consecutive failures.

### 5.2 [LOW] "SYSTEMS NOMINAL" reflects only the WS link, not system health
- **File:** `frame/TopBar.tsx:131` (and `:123` "LAPIS CONNECTED")
- **Appears to user:** "SYSTEMS NOMINAL" implies overall subsystem health.
- **Actually broken:** Derived purely from `connected` (WS up = success). It does not reflect GitHub/PiNyx/quota health, so it can read "NOMINAL" while integrations are offline. "LAPIS CONNECTED" likewise tracks the WS link, not the LaPis endpoint directly.
- **Fix:** Derive from `systemReady` (github.connected && pinyx.configured), or rename to "WS LINK".

### 5.3 [LOW] No client-side router / deep-linking
- The app is a single-view with modal overlays (no React Router). This is a design choice, not a bug, but it means there is no deep-linking to a specific mission or panel — refresh always returns to the persisted `selectedMissionId` only (which is handled). Flagging for completeness; no action required unless deep links are desired.

## CATEGORY 6 — Props & data that never arrive / misleading data

### 6.1 [MEDIUM] "Always visible" Code Context section collapses into permanent disappearance
- **File:** `passive/MissionInspectorPanel.tsx:66-74` (passes `badge="Always visible"` + `showCollapsedSummary={false}`); `passive/CodeContextPanel.tsx:108-116,128`
- **Appears to user:** An inspector section titled "Code Context" with a badge **"Always visible"** and a "▾ collapse" control.
- **Actually broken:** In inspector mode the caller passes `showCollapsedSummary={false}`. The component logic: `if (collapsed && showCollapsedSummary)` → render a clickable collapsed summary (the *only* expand affordance); `if (collapsed && !showCollapsedSummary) return null;` (line 116) → renders **nothing**, with no way back; the "▾ collapse" toggle (line 128) lives only in the expanded branch. So the moment `collapsed` becomes true — either by the user clicking "▾ collapse" **or** by `autoCollapse` firing (which happens whenever the user-enabled `autoCollapseContext` setting is on, per `App.tsx:431`) — the entire section vanishes and cannot be re-expanded until remount (mission change / refresh). The "Always visible" badge directly contradicts the behavior.
- **Fix:** When `showCollapsedSummary` is false, hide the "▾ collapse" control or always render a minimal expandable header. Reconcile the badge with actual behavior.

### 6.2 [MEDIUM] PiNyx gateway status dot/label are hardcoded green; endpoint not editable
- **File:** `active/PinyxConnectionTab.tsx:74-91`
- **Appears to user:** A PiNyx Gateway card with a green status dot and "Managed by Docker", implying PiNyx is connected and healthy.
- **Actually broken:** The dot (`pinyx-status-dot--success`) and label are hardcoded — they don't reflect `config.endpoint`, `configured`, or any reachability check. The only real check is the manual "Check Gateway" button, which is **disabled** when `!config.endpoint.trim()` (line 87), and there is no input anywhere to set/correct the endpoint. So if PiNyx is unconfigured or down, the user still sees green "connected" and, when the endpoint is empty, a disabled button with no explanation of how to fix it.
- **Fix:** Drive the dot/label from real status (e.g. `getPinyxStatus` / last test result); show a clear "not configured" state when the endpoint is empty; add an endpoint input if it's meant to be user-configurable.

### 6.3 [LOW] Mission "Elapsed" stat almost always shows "—"
- **File:** `passive/MissionComplete.tsx:29-52` (elapsed calc), `:120-121` (stat card); evidence `passive/missionUiModel.ts:283-291`
- **Appears to user:** An "Elapsed" stat card on the mission-complete screen.
- **Actually broken:** The calc needs `createdAt` plus a real timestamp on the *last* `WsClientEvent`. The code walks `events` backwards looking for `typeof evt.timestamp === "string"`, but per `missionUiModel.ts:283-291` only the `agent_output` variant carries a real timestamp; every other variant gets a synthetic ordering integer. On any mission that produced no `agent_output` events (failed during planning, aborted early), `lastEventTs` is `0`, so `elapsedStr` is `null` and the card permanently shows "—".
- **Fix:** Derive elapsed from a reliably-timestamped source (mission `createdAt` + terminal time, or the last `logs[]` entry which is stamped with `Date.now()` in the reducer).

### 6.4 [LOW] Sidebar toggle icon is identical in both states
- **File:** `frame/TopBar.tsx:95` (`{sidebarCollapsed ? "☰" : "☰"}`)
- **Appears to user:** The hamburger visually indicates sidebar collapsed vs expanded.
- **Actually broken:** Both branches render the same `☰`; only the `title` tooltip changes. No visual state feedback.
- **Fix:** Use distinct glyphs (e.g. `☰` vs `»`) or rotate the icon.

## CATEGORY 7 — Effects & subscriptions left open / leaks

### 7.0 [HIGH] SettingsPanel calls a hook after an early `return null` — crashes the drawer on toggle
- **File:** `active/SettingsPanel.tsx:13-17` (`if (!open) return null;` at line 13, then `useCallback(...)` at line 15)
- **Appears to user:** A "Settings" drawer that opens/closes cleanly.
- **Actually broken:** Rules-of-Hooks violation: `useCallback` runs **after** the early `return null`. Hooks must run in the same order on every render. `App.tsx` always renders `<SettingsPanel open={settingsOpen} … />` (it is not conditionally mounted), so the same instance persists across open/close. When `open` goes true→false (or false→true) the hook count changes (1 hook vs 0 hooks) and React throws **"Rendered fewer/more hooks than expected."** The settings drawer crashes the first time it is closed after being opened. (Contrast `IntegrationsPanel.tsx` / `QuotaPanel.tsx`, which place all hooks above their `if (!open) return null`.)
- **Fix:** Move `handleBackdrop = useCallback(...)` above the `if (!open) return null;` guard (one-line move).

### 7.1 [MEDIUM] Update "apply" health-poll never terminates on persistent failure; `applying` stuck true forever
- **File:** `hooks/useUpdateStatus.ts:61-83` (poll at 68-78; `.catch(() => {})` at 77)
- **Appears to user:** Clicking "UPDATE" shows a spinning "UPDATING…" chip while the server restarts, then recovers.
- **Actually broken:** After `applyUpdate()` resolves, a `setInterval(getHealth, 2000)` starts and only stops when health returns ok/degraded. If health **keeps failing** (server came back unhealthy, returned non-JSON, deploy failed and never recovers), the `.catch(() => {})` swallows every attempt, the interval runs indefinitely (until unmount), `applyingRef.current` stays `true`, `applying` stays `true` — so the chip shows "UPDATING…" **forever** and the `if (applyingRef.current) return` guard (line 62) blocks any retry. No max-attempts/timeout.
- **Fix:** Add a max poll count / deadline; on exhaustion set `applying=false` and surface "update may not have completed".

### 7.2 [LOW] WS agent_output micro-batch timer not cleared on unmount
- **File:** `hooks/useWebSocket.ts:129-130,183` (cleanup at 221-226 omits it)
- **Actually broken:** `batchTimer` is a local `let` in `connect()`; unmount cleanup clears `reconnectTimerRef` and closes the socket but **never clears `batchTimer`**. A pending `setTimeout(flushBatch, 0)` can fire after unmount and dispatch into a dead reducer. Low impact (0ms window, React 18 tolerates it) but a genuine leaked timer.
- **Fix:** Track `batchTimer` on a ref and `clearTimeout` it in unmount cleanup and `onclose`.

### 7.3 [LOW] `useTabBadge` never restores the document title on unmount
- **File:** `hooks/useTabBadge.ts:6-19`
- **Actually broken:** Neither effect returns a cleanup, so if the component unmounts the title stays in its last mutated state (e.g. `(3) AUREX`). Low impact (app-level hook, rarely unmounts).
- **Fix:** Return `() => { document.title = baseTitleRef.current; }` from the title effect.

### 7.4 [LOW] PiNyx save-flash `setTimeout`s not cleared on unmount
- **File:** `active/PinyxKeysTab.tsx:148-149`; `active/PinyxModelsTab.tsx:109-110`
- **Actually broken:** `setTimeout(() => setSavedFlash(false), 2000)` scheduled but never cleared; switching tabs or closing the drawer within 2s fires `setState` on an unmounted component. (Compare `PinyxConnectionTab.tsx:23-29`, which correctly uses a ref + cleanup.)
- **Fix:** Store the timer id in a ref and `clearTimeout` in a cleanup effect.

### 7.5 [LOW] Debug-log copy-reset `setTimeout`s not cleared on unmount
- **File:** `passive/MissionDebugLog.tsx:25,28` (`window.setTimeout`)
- **Actually broken:** The two copy-state reset timers (1.4s/1.8s) call `setCopyState` after unmount if the panel unmounts in that window. React 18 no-ops silently (no crash).
- **Fix:** Track timer ids in a ref and `clearTimeout` in cleanup, or fold into a `useEffect` keyed on `copyState`.

### 7.6 [LOW] TelemetryBar counter animations not cancelled on rapid updates / unmount
- **File:** `frame/TelemetryBar.tsx:26-38`
- **Actually broken:** Calls `animateCounter` on every `cost`/`tokens` change but does not store/cancel the previous animation instance. Rapid successive updates let multiple anime.js animations race over the same `textContent` (visual jitter), and an animation can keep writing to a detached node after unmount.
- **Fix:** Keep the returned animation in a ref and `pause()` it before starting the next / on unmount.

> Confirmed clean (no leaks): `MissionPipeline.tsx` planning timeout + dot/chip/spinner animation cleanups; `useQuota`/`useBreakpoint`/`useKeyboardShortcuts` interval & window-listener cleanup; `useMission`/`useMissions`/`useSupplyChain` stale-fetch `cancelled` flags.
