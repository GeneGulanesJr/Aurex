# Plan: Refocus Realworld Benchmark on Long-Horizon Agentic Tasks

## Problem

The current benchmark tests **short, single-shot** tasks — fix one function, add one flag, answer one question. Each task is a single `pi --print --no-session` invocation with one prompt and one response. This doesn't measure what matters for real agentic coding: multi-step reasoning, recovery from wrong turns, cross-file awareness, and memory-guided decision-making over extended sessions.

## Design Decisions

- **Keep existing 8 short tasks** — move to `tasks/short/` as a regression suite
- **Use `--print --no-session` with high turn limit** — Pi already chains tool calls within a single invocation. No session model change needed. Tasks are designed to require extensive tool use.
- **Add 5 new long-horizon tasks** in `tasks/` (alongside short/)
- **Keep runner largely the same** — only add: longer timeouts, trajectory grading, warmup/accumulation mode

## Current Architecture Summary

- **Runner** (`bench-pi-realworld.js`): Creates git worktrees, applies patches, seeds memory, runs Pi with `--print --no-session`, grades output
- **8 tasks** across: bugfix(2), feature(2), refactor(1), review(1), staleness(1), negative-control(1)
- **Grading axes**: tests pass, diff touches correct files, answer contains expected facts
- **Memory comparison**: memory-off (isolated HOME) vs memory-on (seeded memories) — measures whether pre-loaded knowledge helps on a single task

## Key Design Changes

### 1. Task Redesign for Long Horizon

Add 5 new tasks that require **multi-step reasoning across the codebase**. The existing 8 short tasks move to `tasks/short/` for regression. New task categories:

| Category                     | Description                                         | Turns Expected | Memory Value                                |
| ---------------------------- | --------------------------------------------------- | -------------- | ------------------------------------------- |
| **cross-cutting-feature**    | Implement a feature touching 5+ files               | 15-30          | High — needs architectural context          |
| **debugging-odyssey**        | Bug requiring investigation across multiple systems | 10-20          | High — needs bug history, past fixes        |
| **api-migration**            | Refactor an API pattern across the codebase         | 20-40          | High — needs design decision context        |
| **architectural-guardian**   | Make changes that must respect known constraints    | 10-20          | Critical — must not violate known decisions |
| **multi-session-continuity** | Task B depends on context from a prior session      | 10-15          | Critical — tests cross-session recall       |

**Concrete task examples** (targeting the LaPis/Pi codebase):

1. **`cross-cutting-add-code-owner`** — Add a "code owner" concept to the memory layer: new DB column, migration, updated search ranking, context injection, and tests. Must touch 8+ files.
2. **`debugging-odyssey-compact-crash`** — A bug where context compaction causes memory loss. Root cause spans 3 modules: session lifecycle, context injection, and the DB layer. Requires reading logs, tracing data flow, and fixing the right place.
3. **`api-migration-hooks-to-events`** — Migrate all hooks from the old callback pattern to a new event-emitter pattern. 10+ files, must maintain backward compat.
4. **`architectural-guardian-no-external-search`** — Implement a search feature that must NOT use external services (known architectural decision stored in memory). Agent that ignores this constraint fails even if tests pass.
5. **`multi-session-continuity-trust-policy`** — Session A establishes a trust policy for a new repo. Session B (fresh, no prior context except memory) must apply that policy correctly.

### 2. Memory Accumulation (warmup mode)

Long-horizon tasks benefit from **naturally accumulated memory**, not just pre-seeded facts:

- **Warmup prompts**: A list of lightweight prompts (questions, small edits, decision saves) run before the main task to build up organic memory
- **`--accumulate`**: When set, each task's memory persists into the next (no wipe between tasks). Simulates a real developer session where memory builds over time.
- For memory-off: still use isolated HOME with no memory extension
- For memory-on: run warmup first (with memory), then the main task

### 3. Enhanced Grading

Add grading axes specific to long-horizon performance:

| Axis                    | What it measures                               | How                                                                          |
| ----------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------- |
| **Task completion**     | Did the agent solve the whole task?            | Tests pass + diff correct                                                    |
| **Efficiency**          | How many turns/tools to solve?                 | Turn count, tool call count                                                  |
| **Self-correction**     | Did the agent recover from wrong turns?        | Detect tool call patterns that indicate backtracking                         |
| **Constraint respect**  | Did the agent respect architectural decisions? | Check for violations of known constraints (must_not_touch, must_not_pattern) |
| **Precision**           | Did it touch only what was needed?             | Diff size (lines changed), files touched                                     |
| **Exploration quality** | Did it read the right files before editing?    | Track read-vs-edit ordering                                                  |

**New grader: `check-trajectory.js`**

- Parses the full multi-turn transcript
- Measures: turns to completion, unique tools used, read-before-edit ratio, backtrack count
- Computes a **trajectory score** (0-1) that rewards efficient exploration

**New grader: `check-constraints.js`**

- Goes beyond `must_not_touch` to support **semantic constraints**
- e.g., "must not import any external search library", "must not use `eval`"
- Pattern-based checks on the diff content

### 4. Runner Changes

The runner stays largely the same (`--print --no-session`), since Pi already chains many tool calls within a single invocation. Key changes to `bench-pi-realworld.js`:

1. **Longer default timeout** — bump from 10min to 30min for long-horizon tasks
2. **`--warmup-tasks FILE`** — runs lightweight warmup prompts to build memory before the main task
3. **`--accumulate`** flag — when set, memory from task N carries into task N+1 (simulating real sessions)
4. **Task discovery** — load from both `tasks/` (long-horizon) and `tasks/short/` (existing regression), with `--only-long` and `--only-short` filters
5. **`--category`** filter — run only tasks of a given category (e.g., `--category cross-cutting-feature`)
